# Interfaces

An Interface defines an explicit interaction contract between architectural responsibilities.
Apply the [REM Interface criteria](../../../rem/models/architecture-boundaries.md#interfaces) to purpose, inputs, outputs, preconditions, failure outcomes, consistency, and compatibility.

The collection uses `<IF-ID>-<full-title-slug>/interface.json` under the [entity naming convention](../../support/README.md#entity-naming-and-filenames).
The draft contracts cover the [IR-001 architecture walkthrough](../README.md#scenario-walkthrough), the proposed [published-product responsibilities](../../requirements/published-products.md), and selected [parent-boundary cooperation](../views/browser/index.html#scenarios). They describe logical interactions and artifact contracts rather than asserting new public runtime APIs or implementation.
IF-003 and IF-004 define the CLI cooperation contract, including fresh guarded writes, exact recovery, and prepublication receipt preparation. The [derived walkthrough](../views/browser/index.html#cooperation) summarizes their contribution to Scenarios and allocated obligations.
Their optional sibling `realization/*.json` files follow the [realization profile](../../support/README.md#subordinate-realization-views). They record attributed process/function bindings and proposed choices separately from those logical contracts.

Participation is derived from Module-owned `provides` and `consumes` references. The single provider is accountable for the Interface contract, including when child Modules realize its behavior. Do not repeat provider or consumer lists in Interface JSON.
Optional `exposed_through` references identify provider ancestors that expose the same Interface. Every intervening provider-side ancestor must also expose it; crossing a parent boundary requires that parent's exposure. Consumer ancestors do not acquire exposure merely by containing a consumer. See the [containment and exposure profile](../../support/README.md) for semantic checks.
MOD-018 provides IF-004 for public command execution; MOD-010 supplies command behavior and MOD-011 retains operational record publication/recovery. MOD-019 provides IF-006 for installation; MOD-014 retains installation behavior and MOD-010 remains the consumer. Neither contract declares `exposed_through`, because its provider already owns the parent boundary. IF-001/002/003/005 retain their child providers and internal scope. The ownership refinement (historical operational reference; original assessment unavailable in the current tree) records that accountability decision without changing the original six Interface identities or operation guarantees.
The parent-boundary contract record (historical operational reference; original assessment unavailable in the current tree) adds IF-007/008/009/010. IF-007 supplies selected-state content and interpretation without retaining a Baseline. IF-008 supplies adopted model-authoring guidance, with other specialist activities retaining their own contracts. IF-009 assesses applicable action authority; IF-010 supplies evidence applicability, coverage, and existing judgment basis. Neither grants approval or performs release qualification, which remains with MOD-015. Their consumers and contributing child responsibilities are explicit in the owning records; no existing Interface was broadened to absorb these distinct guarantees.
Each current Interface has one accountable provider and at least one modeled consumer. Refined REM requires exactly one provider and permits zero or more consumers; the current consumer count is a property of these authored contracts.
An empty set of contracts elsewhere means recorded interactions are deferred, not that the Module needs no cooperation.

The self-contained [Interface schema](../../support/schemas/interface.schema.json) requires identity, title, draft status, description, named operations, consistency rules, compatibility rules, and sources.
Each operation has a unique `snake_case` name within the Interface and explains its purpose, inputs, preconditions, outputs, behavior, and condition/outcome failures.
Operation names identify contract behavior rather than stable first-class engineering entities.
Logical operations alone imply no transport, wire encoding, database, language, or deployment decision. Record material physical choices and observed bindings explicitly in the subordinate view; do not equate a logical operation name with an exported implementation symbol.

IF-001 preserves state and completeness across content access, including rationale availability and applicability.
IF-002 interprets supplied content and checks supplied candidate scope without recursively fetching its own interpretation basis.
Their consistency rules connect identity checking to the state actually retained and prevent mixing different selected states into an apparently complete account.
The written outcomes require later implementation verification; schema conformance alone cannot establish them.

## Customer snapshot boundary

[IF-012](IF-012-qualified-architecture-snapshot-generation/interface.json) is provided by MOD-016 and consumed by MOD-010. It composes generation, check and recovery without repurposing Baseline IF-007. The existing IF-001/004/005 contracts carry scoped capture, admission and candidate refinements; all remain proposed until implementation/adoption.

## Assurance preparation boundary

[IF-014](IF-014-assurance-content-preparation/interface.json) is provided by MOD-017 and consumed by MOD-012 for assessor-supplied assurance content. MOD-007 supplies semantic preparation under [its owning contract](../modules/MOD-017-engineering-governance/modules/MOD-007-engineering-verification-and-assurance/assurance-content.md). IF-010 remains claim-support inspection; explicit recording uses existing IF-004/003. Preparation does not execute verification, retain content or create judgment authority.

## Conformance and model migration preparation

IF-002 now also supplies whole-model conformance and isolated migration preparation under [MOD-003’s contract](../modules/MOD-016-engineering-model-management/modules/MOD-003-engineering-model-conformance/conformance-and-migration.md). MOD-003 coordinates raw IF-001 capture before calling pure supplied-input checks. Existing interpreted retrieval does not recursively bootstrap itself. These logical operations do not expose a new public command or adopt a target profile.

## Baseline custody and controlled state preparation

[IF-015](IF-015-engineering-baseline-content-custody/interface.json) is provided by MOD-016 to MOD-005 and MOD-006 for immutable content custody, isolated recovery and conditional current-model retirement. [IF-016](IF-016-controlled-state-preparation/interface.json) is provided by MOD-006 to MOD-005 and exposed through MOD-017 to MOD-012. It prepares action/transition/retirement meaning for explicit recording without granting authority or inferring effects. [State control](../modules/MOD-017-engineering-governance/state-control.md) owns their composition.

## Lesson and improvement preparation

[IF-017](IF-017-engineering-lesson-and-improvement-preparation/interface.json) is provided by MOD-017 to MOD-012 with MOD-009 contribution. It prepares domain learning content; controlled adoption and generic assurance reuse IF-009/016 and IF-010/014. Existing Learn and selected retention boundaries remain intact.
