# Selected subject history

[MOD-011](module.json) owns FUNC-077 and AR-086 under SR-078. MOD-010 owns AR-087 for public admission and faithful presentation. This is a proposed extension of [IF-003](../../../../interfaces/IF-003-operational-record-access-and-publication/interface.json) and MOD-018-provided [IF-004](../../../../interfaces/IF-004-scoped-public-command-execution/interface.json), separate from the installed v2/v4 current-Change queries. The [record contract](record-contract.md) retains current storage and maintenance authority. No command, schema upgrade or history capability is activated by this document.

## Scope and responsibility

Return explicitly selected facts about a subject across finite retained Changes. History means the records and support actually retained at the captured state, including compact completion accounts; it does not mean every previous edit, deleted observation or invocation. Existing selective retention remains valid. No relevance ranking, engineering decision, live applicability judgment or reconstruction of discarded history is supplied.

MOD-010 validates the selected public operation and converts it into the closed typed history request. MOD-011 alone resolves project association, reads records, matches recorded subject associations, orders results and checks continuation. MOD-010 preserves the resulting scope, state, original provenance, limitations and failure distinctions. MOD-018 owns this child cooperation. No new Module or Interface is needed; existing ordinary query operations retain their no-cursor behavior.

## Explicit subject associations

A subject key is a project-qualified recorded identity: project UUID, identity namespace and stable identifier. The namespace distinguishes, for example, a REM requirement ID from an unrelated identifier with the same spelling. A supplied current path is a display/location hint, not the matching key. A lookup never opens current model files to infer the identity of historical references.

The target storage profile retains explicit associations between that key and a particular record subject occurrence. Each association identifies the Change, record kind and ID, original subject field/occurrence, original path, state and content identity or the original explicit unavailable basis, and the attributable supplied association source. It preserves the original record and judgment. Different revisions and renamed paths can share a recorded key; a reused path or equal display name cannot establish continuity. Conflicting recorded association claims remain visible and prevent unqualified complete subject coverage.

Existing path/hash-only v4 subjects are not automatically upgraded to stable keys. An explicit, attributable mapping may be supplied under a separately authorized recording or migration operation only when its support establishes the association. Unmapped or ambiguous retained occurrences remain disclosed coverage gaps; they are never silently omitted as nonmatches. An exact original-basis selector may inspect those known occurrences, but cannot claim stable-key coverage across other revisions. Matching a supplied assertion reports the recorded relationship, not independent proof that its author identified the subject correctly.

The target profile needs a storage-owned subject-association relation and coverage metadata, not a second authoritative copy of records. Associations reference retained typed record locations and original subject bases; referential validation rejects dangling or contradictory active mappings. Subject-bearing writes, compaction, retirement and import preserve or explicitly dispose of these relationships and update coverage in the same record transaction. A query cannot backfill associations or repair an index. An index may accelerate selection only when derived from these same authoritative rows and transaction state.

## Typed selection and result

The separately proposed history request supplies the operation/profile, associated project, explicit finite Change population or explicit all-retained scope, one subject key or exact original-basis selector, recorded-fact filters, page bound and optional continuation. Defaults must be normalized and echoed; an omitted scope cannot become a hidden whole-store search. The public adapter owns the eventual versioned wire grammar. Its qualification must precede advertisement; adding a logical operation here does not broaden current targeted-recording-v2 or its closed schemas.

Supported filter meanings are literal record kinds/IDs and existing recorded finding dispositions or Verification outcomes, using their owning contract's admitted values. Filters compose by intersection. An empty filter means all records in the otherwise explicit subject/population scope. MOD-010 rejects unknown request keys/filter values, invalid byte/count bounds and contradictions visible in the explicit request before dispatch. It treats the continuation as bounded opaque input; MOD-011 authenticates it and checks its bound selection and current state during coherent acquisition, before returning any page units. Command admission does not require the protected key, decoded cursor fields or live database state. A filter does not inspect prose for relevance or infer present applicability from a historical judgment.

A result unit is an identified subject association to a retained record, with its originating Change, typed record identity, original subject basis, recorded relationship path and provenance. A finding filter applies only to a finding whose association to the subject is explicitly recorded; merely belonging to a Review that mentions several subjects does not associate every finding with every subject. Verification filtering likewise uses the identified retained Verification relationship and recorded outcome. Missing association detail is a coverage limitation, not a semantic guess.

Return bounded complete result units, normalized selection, observed history state, ordering, explicit exclusions/coverage gaps, page exhaustion and any continuation. Keep page exhaustion separate from retention/association completeness. Only an exhausted selection over an available, supported and completely accounted-for retained scope can be empty and complete. Even then its meaning is no match in that retained scope, never no relevant work in all time. Known compacted detail, absent/unreadable stores, unsupported profiles, unavailable associations and missing retained support have distinct explanations.

Referenced payload contents are not silently loaded as part of selection. Return their retained identities and availability scope; a metadata-only result does not prove payload readability. Required unavailable metadata or corrupt records make the affected scope incomplete or unavailable. Detail retrieval is a separate explicitly selected operation and must retain its original record/state association. A successful history query supplies neither current approval nor a safe-to-proceed recommendation.

## Coherent read and continuation

Use one short read-only SQLite transaction per page under the existing ordinary-access/maintenance exclusion protocol. History acquisition must use an existing associated, supported store and qualified read-only access. It must not create a database, initialize sidecars as an application operation, replay a record task, select recovery, activate a staged replacement or run a migration. If the selected platform/store condition requires recovery or writable initialization to establish the read, report unavailable and leave that action to an explicitly authorized owner. Maintenance fences and unavailable/busy outcomes remain effective. No transaction or lease survives between pages.

Read the history state, coverage metadata, subject associations and selected record facts from the same transaction snapshot. Check project/schema/profile and continuation state before returning any page units. Material malformed or unsupported records cannot be skipped to produce complete coverage. Unavailable members may produce explicitly incomplete bounded results only when the available subset and exclusions are identifiable; otherwise return unavailable without fabricated partial success.

The target profile adds a durable history generation and activation identity owned by MOD-011. Every successful record/association/coverage change advances the generation in the same transaction, including compaction and import; rolled-back transactions do not. Use a checked monotonic integer and refuse an overflowing target-profile mutation before effects rather than wrapping. Explicit activation, restore, transfer or replacement provisions a fresh activation identity and continuation key, even when restored content and project UUID equal an older state. Old tokens must not revive after a restore or change-and-revert sequence. This metadata describes live query state, not a rewritten historical assessment.

The qualified writer population must enforce that generation rule. A schema/profile capability check fences incompatible older writers; a partially upgraded store cannot advertise history support. A migrated source with missing association coverage reports that gap rather than inventing a complete past. The new metadata and writer rules require explicit profile/schema qualification and authorized migration before use. The current v4 schemas, executable and maintenance operations are unchanged by this Design. No fallback to timestamps, file sizes, per-Change revision alone or a digest of an incomplete selection is allowed.

Order result units lexicographically by Change ID, record kind, record ID and stable occurrence identity using a defined bytewise encoding, not locale or timestamps. The tuple is unique within the captured scope. A page resumes strictly after its last returned tuple. The cursor binds project, activation, generation, normalized complete selector/filter/order/page-bound identity and last tuple. MOD-011 emits an opaque authenticated encoding under the activation's protected key; validation rejects malformed, altered, unsupported, wrong-project or mismatched-selection tokens before results. The key is provisioned by the authorized profile activation, never generated or persisted by a read. Authentication protects cursor integrity and does not grant engineering authority.

On any generation/activation change, reject continuation as a conflict, return no page units and require a fresh first-page request. Do not merge snapshots or restart implicitly. A writer committing after a page's read snapshot does not invalidate the page's attributed old state; the next page detects the changed state. Repeating the same admitted cursor against the same state yields the same page. The store retains no cursor session, reservation or per-query record.

## Bounded public outcome

MOD-010 admits a finite page count and the public byte bound before dispatch; the proposed operation retains the existing 1 MiB public response ceiling. MOD-011 applies the shared pure result encoder/budget calculation while constructing the page, with room for state, limitations and cursor. Request and token byte bounds are fixed by the qualified public profile; the proposed token bound is 4 KiB within the existing 1 MiB request ceiling. Boundary admission counts encoded bytes, not characters.

A page stops only between complete units and reports the exact continuation boundary. If one selected unit or mandatory diagnostic cannot fit, return a bounded explicit too-large result without advancing past it or truncating narrative. An empty page cannot carry a success cursor that loops at the same boundary. Exhaustion requires actually checking the remaining selected scope, not assuming fewer-than-requested units means complete.

Serialize and validate the full bounded outcome before writing stdout. MOD-010 preserves conflict, busy, unavailable, incomplete and too-large meanings and cannot relabel them an empty complete result. Output failure leaves the read without record effects; a retry against changed history may conflict rather than reproduce the old page. Diagnostics remain bounded and private under their existing owner. Subject content and continuation secrets must not leak into unrelated logs.

## Realization, compatibility and acceptance

The selected realization extends the existing local Node/SQLite ownership: MOD-011's typed domain query and association/state adapter perform selection in one database read snapshot; MOD-010's admission and pure codec provide the external boundary. The database and protected activation metadata stay project-local. No service, background indexer, filesystem-history scan, distributed merge or retained pagination session is introduced. The [parent-owned Process diagram](../../README.md#selected-subject-history) shows the cross-child interaction. These choices describe target software organization and physical placement, not observed source bindings.

Delivery must qualify the complete writer, read-only acquisition and maintenance population together, including association migration and activation invalidation. Until that separately authorized work succeeds, capabilities must report this history extension unavailable. Current v2/v4 behavior and independently versioned contracts continue unchanged. The proposed IF-003/004 operations do not imply installed command syntax or permit older clients to send new fields to existing operations.

Use independently prepared synthetic records in two Changes, including a renamed subject, two revisions, an unrelated same-name subject, an unmapped historical occurrence and a multi-subject Review. These Design walkthroughs allocate future proof; they are not executed query evidence.

| Obligation and failure | Required observation |
| --- | --- |
| SR-078 C1/C5; AR-086: wrong identity or provenance | Match only the explicit project-qualified key; preserve both original revisions/paths and record origins. Do not join an unrelated same-name/path subject or fabricate mappings for old path-only facts. |
| C2; AR-086/087: guessed finding relevance | Literal finding/Verification filters use actual recorded associations and values. A Review-wide subject list cannot manufacture finding-specific relationships; unknown filter values reject. |
| C3; AR-086/087: false complete empty result | Contrast complete no-match with absent storage, unsupported profile, missing association, compacted detail and corrupt records. Page exhaustion never erases a retained-scope limitation. |
| C4; AR-086: changed pages or cursor tampering | Compare fixed-state repeat/next pages, changed filter/project/order, altered token, concurrent committed mutation, change-and-revert, restoration of old bytes and generation overflow. No changed-state continuation returns partial results or silently resumes. |
| C6; AR-086/087: writes during lookup | Observe missing database, recovery-needed state, sidecar initialization requirement and maintenance fence. Lookup neither creates/repairs storage nor changes model/assessment state. Verify actual supported read-only platform behavior before capability qualification. |
| Public budget and handoff; AR-087 | Multibyte response at the byte cap, one oversized unit, empty limited page, unavailable detail and stdout failure retain whole units and exact scope. No omission is labeled full coverage. |

Independent integrated Design review must judge these interactions against all six SR criteria. Executable query, migration, concurrency and platform tests belong to later delivery; schema conformance and the browser diagram do not establish runtime availability or implementation satisfaction.
