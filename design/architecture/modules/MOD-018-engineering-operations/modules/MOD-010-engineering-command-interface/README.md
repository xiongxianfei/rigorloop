# Command interface: successor workflow operations

This is the proposed `targeted-recording-v2` interface for [v4 operational records](../MOD-011-operational-record-persistence/README.md), under AR-040 and the Operations parent composition. These spellings are design inputs for implementation, not currently available commands. Skills must keep using actually supported capabilities until coordinated adoption. The implemented [v1 CLI contract](../../../../../../docs/design/cli/cli.md) remains unchanged by this document.

## Admission and version domains

The successor runtime serves targeted-recording-v2 requests with `schema_version: 2` and `contract: "rigorloop-records-v4"`. Results identify `interface: "targeted-recording-v2"` and `schema_version: 4` from recognized command dispatch, including pre-store failures; a result version does not imply a validated record store. V1 clients must reject it explicitly. A new runtime rejects old request versions/contracts rather than translating them. The build and installed capability report must identify the served interface and record contract; recording availability cannot be inferred from a skill name or package installation.

Keep explicit `--root PATH`, `--change ID`, `--input -`, `--format json|text` and mutation-only `--dry-run`. Unknown/duplicate flags and positionals reject before repository access or stdin consumption. Query selectors are explicit and bounded; there is no automatic entire-store dump, stage advancement, authority grant or choice of the next activity. `subject inspect` admits explicit paths and reports present identities or observed absence; it neither invents deleted content nor changes historical subjects.

The proposed `capabilities --root PATH --format json|text` read requires no Change or stdin. It returns the closed item `{interface: "targeted-recording-v2", record_contract: "rigorloop-records-v4", workflow_contract: "requirement-first-v1", operations: [Text], backend_available: boolean, limitation: Text or null, identity: Digest}`. Operations are exactly the supported command catalogue below, sorted lexicographically; no speculative operation is advertised. Identity hashes canonical UTF-8 JSON of all preceding fields with keys sorted and no insignificant whitespace, excluding identity. The runtime probes its selected adapter before reporting backend_available; false carries an explicit limitation and true requires null. This reports capability, not a validated Change or successful recording. A subsequent operation repeats its own availability checks.

One mutation envelope is exactly `{schema_version: 2, interface, contract, change_id, expected_revision, reads: [Subject], operation: Operation}`. Batch replaces operation with `operations: [Operation]`, 1–64 entries. Subject is the v4 closed present/absent type. `expected_revision` is an opaque Digest; it is null only for standalone creation. Selectors and body must agree. `Operation` is exactly `{op, target, values}`. Set operations require a nonempty subset of their listed mutable fields; omitted fields remain unchanged and null is admitted only by the stored type. Unknown fields reject before consistency inference. No raw SQL, file paths, array offsets or generic patches are accepted as record selectors.

Requests are capped at 1 MiB of UTF-8 input; external read subjects are bounded by that byte limit rather than the operation-count limit, so a whole-change decision can guard more than 64 files. Selected query content is capped at 1 MiB before result rendering; exceeding it rejects with a bounded size-limit diagnostic rather than silently dropping records. Artifact payloads are not returned inline. These limits are independent of the backend's historical store size.

## Closed operation catalogue

Stored field types and full record contents are defined once by the Records owner. A complete record input below omits only engine-owned schema_version, contract, change_id and id. Engine bookkeeping never supplies an actor decision or rationale.

| Operation and public command after `rigorloop` | Target | Values and effect |
| --- | --- | --- |
| `change.create` / `change create` | `{}` | Complete Change content. Requires absent Change; creation is excluded from batch. Empty lists, null basis/plan/adoption and initial activity are explicit inputs. |
| `change.set` / `change set` | `{}` | Nonempty subset of requirement_basis, design_basis, plan and active_adoption. Referenced records must exist and match their declared purpose; this records selection, not renewed authority. |
| `activity.set` / `activity set` | `{}` | Complete activity object. No transition is inferred from a status. |
| `request.add` / `request add` | `{id}` | RequestSource without id. Preserve the original capture; correction is another attributed input. |
| `work.add`, `work.set` / `work add`, `work set` | `{id}` | Complete Work without id for add; nonempty subset of status, owner, requirement_refs, check_refs, blocker_ids, completion_reason for set. No approval fields. |
| `gate.add` / `gate add` | `{id}` | `{target, applicability_ref: null}`. Target and identity are immutable; one per assessment purpose. |
| `gate.set` / `gate set` | `{id}` | `{applicability_ref: Ref or null}`. Selects or clears reliance without changing historical records. |
| `basis.record`, `candidate.record`, `review.record`, `evidence.record`, `decision.record`, `applicability.record`, `verify.record`, `adoption.record` | `{id}` | Complete corresponding immutable record content. Public spelling replaces the dot with a space; `verify` stores Verification. Existing exact content is an unchanged retry; different content with the same ID rejects. New Review must have empty finding_updates. |
| `finding.add` / `finding add` | `{review, id}` | Complete Finding without id. Append to that Review, preserving its assessment core and existing findings. A late finding is exposed on every scoped reliance read. |
| `finding.set` / `finding set` | `{review, id, update_id}` | `{actor, reason, account: Finding}`. Appends a FindingUpdate to an existing finding; account.id equals target.id. Reusing update_id with different content rejects. |
| `blocker.add` / `blocker add` | `{id}` | Complete Blocker without id. The immutable Origin must equal the supplied initial reporter/subjects/evidence/required_outcome; actor supplies rationale and optional supporting_review. |
| `blocker.set` / `blocker set` | `{id}` | Nonempty subset of current Finding fields other than id; state/resolution are supplied together. Origin cannot be named, removed or changed. |
| `batch` | Not a nested operation | One explicit ordered list of the above operations except change.create. Validate the complete candidate and publish atomically; no partial batch receipt. |

V4 has no `review.set`, `verify.set`, path-based `applicability.set`, mandatory proposal `change.link`, delete, auto-approve or auto-advance operation. A changed assessment is another attempt. Explicit basis/candidate/record creation and pointer selection can be one batch without requiring complete future-stage records or automatic registration. Review creation may refer to an earlier proposed basis; accepted basis creation refers to the resulting review without circular references.

Reject repeated or overlapping semantic assignments within a batch even when their values agree. Distinct record creation, updates to separate fields and explicit finding append/current-account operations may compose when their destinations do not overlap. Creating a gate with null applicability and then setting that same field in the batch is an overlapping assignment; create the gate earlier or supply the complete initial Gate in standalone Change creation. Reference validity is checked against the complete candidate, so a preexisting gate can select an Applicability created in the same batch.

## Bounded reads and observations

`status` returns recorded activity and aggregate work, finding, gate and evidence counts, with drift/availability diagnostics; it is not a next-stage recommendation. `context --input -` uses exactly `{schema_version: 2, interface, contract, selectors: [{kind, id}], include_observations: boolean}` with 1–64 selectors. Kind is `change`, `work`, `gate`, `basis`, `candidate`, `review`, `evidence`, `decision`, `verification`, `applicability`, `adoption`, or `blocker`. Change selector uses the selected change ID. All other IDs select exactly one record or embedded entry, not a name search. The CLI returns selected complete objects and explicit truncation/size rejection, never a quietly incomplete basis. Finding reads use `finding show ID --review REVIEW-ID` and include original Finding plus current account and its updates.

The same selection supports `<kind> show ID` for work, gate, basis, candidate, review, evidence, decision, applicability, adoption and blocker. `verify show ID` selects Verification; it is no longer a success-only singleton. `change show` selects the current Change. Gates return their selected applicability plus bounded exact review/candidate references, not all historical attempts. Follow referenced IDs explicitly when more history is needed. No latest timestamp establishes authority. Missing required references, payloads and subjects are distinguished from empty results.

Each result item is `{kind, id, value}`. Kind is one of the context selector kinds, `finding`, `subject`, `capabilities`, or `status`. ID is the exact selected ID, except a Subject uses its Path and capabilities/status use null. Value is the corresponding closed v4 record/entry, Subject or capability item. Finding value is `{original: Finding, current: Finding, updates: [FindingUpdate]}`. Status value is `{activity, counts: [{kind, count}]}` with nonnegative integer count and one row each for work, blocker, finding, gate and evidence; these are totals, not readiness scores. Related gate records are separate identified result items. Errors and observations use the diagnostic shape below; a query does not quietly substitute an observation for missing required selected content.

For reliance, inspect the exact candidate and applicable policy/guidance dependencies, then provide their external Subject read set and the coherent store revision with the decision. The semantic owner must select an adequate set; the CLI verifies what was declared and cannot prove that an omitted dependency was irrelevant. Governance supplies judgment and authority; a successful read/save does not advance the workflow.

## Result and retry contract

The closed result is `{schema_version: 4, interface, operation, status, claim: "storage-only", errors, observations, items, changed, committed}` plus optional change_id, revision and record_contract. `operation` is the recognized catalogue name, `capabilities`, `status`, `context`, `subject.inspect`, the recognized show command with spaces replaced by dots, or `batch`; unknown commands use null. `record_contract` is present only after validation establishes v4. `revision` is present only for a coherent inspected state. `items` contains selected typed v4 values or the defined capability item; mutation receipts do not echo whole records. `changed` contains `{kind, id}` for committed changes only; it is empty on preview, unchanged and failed publication. Diagnostics are `{code: Text, message: Text}` with safe selected identifiers in prose; never echo malformed selectors or secret payloads. Diagnostic codes are an extensible text domain, not a closed workflow vocabulary.

Changed kinds are exactly `change` plus the supporting Ref kinds. Changes to embedded work, gates, requests and blockers report their containing Change once; finding changes report their containing Review once. Deduplicate receipt entries and sort by kind then ID. Neither a successful receipt nor an unchanged immutable retry clears findings or changes a reliance pointer implicitly.

Status and exit are `ok/0` for reads, `saved/0`, `unchanged/0`, `preview/0`, `rejected/2`, `conflict/3`, `busy/4`, `recovery-needed/5`, or `failed/1`. `committed` is true only after confirmed publication, false when no commit occurred, and null when the outcome is uncertain; a confirmed write followed by reporting failure uses failed/1 with committed true, no success claim and the known revision if available. No failure returns a partially successful changed list. Standard diagnostics include invalid-input, unsupported-interface, unsupported-contract, target-not-found, target-exists, broken-reference, stale-revision, subject-drift and artifact-unavailable; internal errors must not be relabeled as absence.

Dry-run performs the same candidate checks and reports preview with committed false, without reserving IDs or promising later success. Fresh mutation repeats all checks. On stale revision, reread and reassess rather than replay the same decision against a new revision. On uncertain outcome, query the exact requested record IDs and coherent revision before retry. The unchanged-create rule is evaluated only after the request's revision and read set are current; it does not bypass concurrency checks.

## Test design and compatibility

Concrete implementation must test every new closed vocabulary with an unknown-value negative case before consistency checks, preserving current parser, containment, transaction and privacy protections. Test command/body mismatch, old transport against new runtime, unsupported backend, same-ID identical/different retries, absence becoming presence after inspection, omitted selector rejection, query bounds and output failure after commit. Use real selected storage and filesystem boundaries for transaction/race cases, not a mocked successful publisher.

The parent [Operations test design](../../test-design.md) owns semantic whole-workflow adequacy; these tests own admission and truthful representation. Full v4 JSON Schema artifacts and dispatch code are implementation deliverables of this exact field/operation specification, not claimed to exist now. The older advanced file-replacement API is not exposed by v2; backend recovery remains internal and explicit historical import has a separately authorized migration boundary. This keeps physical file layout out of skill contracts and permits the selected SQLite realization without teaching skills storage mechanics.


## Browser command family

The proposed `browser-v1` family realizes [IF-012](../../../../interfaces/IF-012-qualified-architecture-snapshot-generation/interface.json). It is separate from `targeted-recording-v2`; no Change creation, lifecycle approval or SQL access occurs. Proposed invocations are `rigorloop browser generate`, `rigorloop browser check` and `rigorloop browser recover`. These names are target design, not available commands or entries in the observed command catalogue.

RigorLoop's own repository is the first consumer of this same packaged boundary. Its thin generation wrapper supplies explicit project, immutable selection and output inputs; there is no repository-only command mode or bypass of capture/publication checks. The initial profile identifies one fixed supported model contract. Additional configurable profiles and independently distributed templates are outside the first adoption; unknown profiles still reject. [MOD-004's first-project design](../../../MOD-016-engineering-model-management/modules/MOD-004-engineering-context-and-traceability/README.md#rigorloop-as-the-first-supported-project) owns projection and migration boundaries; packaging qualifies the actual installed candidate.

The existing Node JavaScript ESM command layer is a thin adapter to the packaged Rust browser engine under [the technology decision](../../../MOD-016-engineering-model-management/modules/MOD-004-engineering-context-and-traceability/README.md#technology-decision). Preserve the public CLI and existing unrelated commands. Node owns argument admission, platform/resource checks, shell-free child launch, cancellation and result presentation. The engine owns model interpretation, generation and output mutation/recovery. The repository wrapper invokes this same public boundary rather than launching a different engine directly.

Use the bounded internal `browser-engine-v1` JSON request/result protocol with exact request and resource identities. Do not expose it as another supported customer command or equate its version with public `browser-v1`. Reject mismatched/unknown protocol results before reliance. A child launch failure before execution may establish no engine mutation; termination, malformed output or response loss after launch cannot establish precommit failure. For a potentially mutating operation, preserve the selected output/request identity and report `recovery-required` unless a valid result establishes the actual outcome. Never silently retry, erase recovery state or convert a child exit status into a successful generation claim. Check-mode failures retain their nonmutating meaning.

`generate` requires explicit project/profile, immutable input selection and output. Replacing an existing owned output also requires explicit replacement intent and exact expected current entry identity. `check` compares the same source/tool scope and existing output without mutation. `recover` requires the specific owned output, interrupted operation identity, expected state and bounded recovery disposition; it does not replay generation against newly read facts. Output selection and supported platform/renderer compatibility are admitted before any writer acquisition. Never default to the nearest operational Change or database.

Results identify `browser-v1`, operation, project/profile, captured input identity when available, generator/renderer resource identity, selected output, actual commit identity, diagnostics and unresolved scope. The closed outcome set is `generated`, `current`, `stale`, `recovered`, `rejected`, `failed`, `committed-with-reporting-failure` and `recovery-required`. `generated` applies only after complete generation commitment; `current`/`stale` are check outcomes, not quality judgments; recovery reports the actual selected version. Reject unknown operations/outcomes before consistency checks. Publication, verification success and review approval are never inferred from these values.

The exact machine serialization and platform-specific interruption mechanisms must conform to this semantic contract when implemented; this does not add a schema to the currently supported CLI. Evidence must cover incompatible dependencies before writes, absent/stale expected identity, safe output boundaries, check-mode nonmutation and truthful post-commit failure. MOD-004 owns output recovery, MOD-010 preserves its outcome; neither owner silently repairs source definitions.
