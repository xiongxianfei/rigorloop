Existing model, projection and browser checks prove structure/presentation only. Delivery allocates runtime proof after the refined design is assessed.

Distinguish mechanically compared scope from an actor's report that nothing changed. A timestamp or a commit name alone cannot establish an unchanged working tree. Missing comparison information remains visible; do not force comprehensive snapshots merely to prepare review.

For compaction, compare removable superseded detail with an open issue, a selected Review in an active Change and a completion-selected attachment. Refuse removal of surviving dependencies; closed compaction can clear obsolete selectors only for explicitly dropped records. Allow cleanup of unneeded detail without requiring historical copies. A shortened context cannot hide omissions behind an apparent success. Support summaries are assessment-owned context, not a duplicate current evidence record editable by implementers.

Attachment and concurrency cases need real byte/storage effects when implemented; a mocked successful copy or parser-only test is insufficient. Use fresh isolated fixtures and independently authored expected states. SQLite journals are storage machinery, not an engineering activity archive. Include project/schema mismatch, failed attachment metadata commit, cleanup racing a new reference and coherent backup/restore with retained payloads in adoption proof.

The [recording sequence](README.md#record-a-handoff-update), [lost-response sequence](README.md#discover-a-saved-update-after-a-lost-response) and [storage transaction states](modules/MOD-011-operational-record-persistence/README.md#transaction-states) make the existing SCN-046/047 boundaries inspectable with the same navigation-update example. Check attachment capture without record commitment, interruption during publication, commitment without response delivery, and a newer intervening writer. The intended observations are respectively an unused copy without false evidence, a coherent SQLite snapshot or explicit unavailability, context reconciliation without replay, and refusal to overwrite newer work. Diagram rendering proves presentation only; these storage outcomes still need implementation proof.

[Governance test design](../MOD-017-engineering-governance/test-design.md) retains SCN-082 adoption/recovery. Existing supported v1/v3 tests remain applicable to their runtime; these proposed changes do not silently retire their compatibility coverage. [CLI](modules/MOD-010-engineering-command-interface/README.md#walkthroughs-and-acceptance-intent) and [Records](modules/MOD-011-operational-record-persistence/README.md#test-design) own child admission, reference, bounds and publication observations. The group set is sufficient for this design refinement; it is not an exhaustive future test whitelist or execution claim.

## SQLite schema and maintenance observations

Reuse SR-043–047 and SR-074–077. The [storage owner](modules/MOD-011-operational-record-persistence/README.md#relational-schema-and-query-boundaries) owns the mapping, software organization and maintenance sequences. The following are design allocations for later implementation, not new executable cases or a qualification claim.

| Distinct failure to expose | Representative setup and independent observation |
| --- | --- |
| Record relationships cross Change boundaries or erase retained meaning | Two Changes reuse a Review ID. Reject a cross-Change relation; reject an account without its typed row; admit a valid deferred Basis/Review cycle. Omitted findings survive. A reviewed Evidence replacement changes support standing in the same transaction. |
| Numeric revision loss or stale overwrite | Use a revision beyond JavaScript's safe integer range; round-trip the opaque token exactly. Two real CLI processes read one revision; one commits and the stale writer preserves the winner. Restore rotates incarnation, so an old token still rejects when numeric Change revision repeats. |
| Update and payload disagree | Fail after named-file publication but before database commit; inspect old records and the unused copy. Race explicit cleanup against new retention; writer exclusion preserves the newly referenced bytes. A missing required old file remains a visible limitation. |
| Backup mixes snapshot and payload scopes | Backup a selected Change while another actor attempts recording/cleanup. Inspect the snapshot, selected/excluded IDs, database integrity and exact independently known payload bytes. Fence admission must prevent incompatible capture; loss of a required payload prevents complete publication. |
| Restoration crosses authority or claims partial success | Try wrong project, altered digest, escaping member, occupied destination with stale expectation and unreadable destination without observation. Each rejects before activation and preserves unrelated paths. Interrupt between database/attachment moves; ordinary access remains fenced. |
| Maintenance recovery overwrites later work | Interrupt before activation and exercise guarded finish/rollback from the actual manifest; foreign bytes block both. After activation, lose the receipt, release the fence and create later work. Old rollback and stale replacement requests must reject. |
| Maintenance admission has a check/open race | Pause an ordinary caller between its first fence check and lease publication while maintenance drains observed leases. Its second check must prevent database access; uncertain or reused owner identity cannot be force-cleared. An unused fence after a busy attempt is removed only by its owner. |
| Import turns historical direction into new approval | Classify supported, retained and blocked legacy records. Preserve source byte identities and all unresolved obligations; a Proposal/milestone judgment cannot become requirements/whole-change approval. A blocked disposition or changed source prevents activation. |
| The packaged runtime differs from the design | Run the actual packed CLI on each supported Node/platform candidate. Check binding API, effective WAL/FULL/FK settings, packaged migration availability, backup behavior and JSON/diagnostic separation. A local binding experiment alone cannot establish this product qualification. |

These cases cover the new reference, activation and external-byte boundaries. Existing tests for the supported v3 store remain valid; presentation checks only establish that the design and generated browser agree. Delivery must allocate real-process interruption and actual filesystem/database assertions before claiming the SQLite replacement usable.

## Public and internal interface observations

Use the [complete review-record walkthrough](modules/MOD-010-engineering-command-interface/README.md#review-recording-walkthrough) and [composed sequence](README.md#record-a-review-assessment) to assess SR-040–045 at IF-004/IF-003. These are acceptance observations for future delivery, not additional executable cases now.

| Representative variation | Independent observation and failure exposed |
| --- | --- |
| Valid prepared Review with explicit assessor judgment and reported applicability | Observe Review, Change selection and revision committed together; Verify remains outstanding and no independent judgment is manufactured. |
| Unknown flag, discriminator, duplicate key or task member; conflicting scope | Observe early rejection before dependent access; flag/help admission must not consume stdin or open project data. JSON admission necessarily reads bounded stdin. |
| Existing open finding omitted from the submission | Inspect the retained finding independently of receipt status; neither empty findings nor a clean new summary resolves it. |
| Stale revision, busy writer, rollback, unknown commit and lost successful response | Compare code/status/committed with independently observed stored effects. Unknown never becomes false; a lost receipt never triggers semantic replay. |
| Large optional changed-entry set versus oversized mandatory receipt | Observe explicit omitted counts and bounded output. Failure to prepare mandatory receipt rejects before commit; output failure afterward preserves actual commitment. |
| Typed task consumer attempts to provide SQL, a connection or a construction/render callback | Observe rejection at the closed v4 boundary; the fixed internal pure receipt codec is not caller-supplied authority. |
| Ordinary recording and store maintenance receive stdin versus filename flags | Observe consistent --input - admission, with distinct envelope/version and Change versus whole-store expectations. |
| Supported v3 recovery beside target v4 opening and maintenance resume | Retain each contract's observed behavior. No v3 file-repair task or manual ordinary SQLite recovery is inferred from v4 diagnostics. |

Existing browser checks validate the registered sequence and navigation only. They cannot prove transaction atomicity, reviewer independence or the proposed request/result implementation.

The successor-package compatibility boundary requires real dispatch proof: identical review-show spelling follows the executing package contract; v1/v3 envelopes and retired commands reject in the successor; absent v4 storage cannot fall back to a legacy directory. Preserve the qualified previous executable for bootstrap/recovery and exclude its concurrent writers before import.

For bounded retrieval, fill one Review and one Change near their admission limit with retained Issues, including deferred and previously disposed cases. Measure the complete encoded selector response and reserved growth independently, including escaping and long opaque identities. Submit maximum-sized valid dispositions without deleting finding meaning and read them back. Compare an oversized disposition, an additional Issue exceeding remaining capacity and an import that would strand an account: each must reject before commitment. Aggregate-context overflow must expose a usable smaller selector; it does not permit admitting an individually unreadable account. Starting with only a Change ID and no chat context, follow the supplied Change-only discovery request, enumerate the complete account index and read an open finding in an unselected advisory Review. Attempt growth beyond index capacity and observe precommit rejection with the old complete index still available.

### Recorded acceptance and current support

For the SR-040–046 admission/result and SR-074–077 persistence scope, begin with an accepted Basis linked to its current approved formal Review. Replace supporting Evidence with a contradictory result or record an adverse Review assessment. Observe that the corrective record saves, the Basis retains its attributable accepted decision, and context exposes unsupported current reliance. Successful final Verify and closeout remain unavailable until the required support is reconciled and Verify explicitly reassesses it. In contrast, a newly created or replaced accepted Basis without current compatible approval rejects before commitment. This distinguishes truthful current-state correction from fresh acceptance admission; a blanket perpetual-approval validator would fail the correction observation.
