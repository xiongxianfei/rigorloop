# Skills and commands: workflow integration test design

Apply the [System-owned shared test rules](../../../../docs/design/test-design/rules.md). The following groups specify observation intent, plausible defects and necessary boundaries; Delivery later assigns exact commands and implementation supplies fixtures. Existing schema/projection tests protect shape and derived views only. No current executable suite is claimed to prove the target workflow.

Additional integrated proof must cover the stale-read race between review and activation, reporting failure after a committed record write, and a missing installed conditional reference despite valid canonical sources. Child conformance can pass while these interactions fail. Start from a valid fixture, vary the named defect, inspect actual results and preserved state, and keep unknown-value rejection separate from cross-field inconsistency.

Together with the Governance adoption group, these groups cover the selected SR criteria and affected shared behavior through positive, negative, correction and adoption outcomes. They are not an exhaustive test whitelist. Runtime proof remains unimplemented; design review should challenge the walkthroughs and boundary choices before Delivery allocates their concrete realization.

SCN-082 adoption/recovery belongs to [Governance test design](../MOD-017-engineering-governance/test-design.md). Child contracts and existing executable checks retain their separate scopes.

The [MOD-010 command groups](modules/MOD-010-engineering-command-interface/README.md#test-design-and-compatibility) and [MOD-011 record groups](modules/MOD-011-operational-record-persistence/README.md#test-design) refine representation, reference integrity, immutable attempts, bounded reads and committed-output-failure proof. Parent integration must also test that structurally valid approval with stale subjects or new contrary findings cannot support a final-success claim. A code candidate alone is insufficient without current governing basis and authority.
