# Model conformance and migration preparation

MOD-003 owns FUNC-002/012/013/014, existing AR-003/010/058 and IR-005 AR-067–069. The new obligations concern whole-model diagnostics, distinct mechanical-result presentation and explicit migration candidates. Existing identity, interpretation and relationship-admission contracts remain separately scoped. This is target Design; repository validators do not establish that the proposed product engine is implemented.

## Responsibility and input boundary

An engineering participant selects a model/state and declared profile, a conformance scope or explicit migration mapping, and any supplied review or consumer-assessment inputs. MOD-003 owns the logical request, pure assessment/transformation and result explanation. No new CLI command, public protocol or automatic profile adoption is defined. Existing consumers of IF-002 may supply captured content directly; the new `check_model_conformance` and `prepare_model_migration` operations do not fetch their own inputs.

For a participant-facing current-state request, MOD-003's acquisition coordinator uses MOD-001's IF-001 `capture_model_selection` before invoking its pure checks. MOD-001 binds one immutable read basis or supplies content under sufficient read exclusion, including complete relevant membership and bytes. A supplied immutable export uses the same explicit content/membership basis. MOD-003's IF-002 operations only interpret the supplied raw content; they cannot call interpreted retrieval to bootstrap their own interpretation. This breaks recursive storage/interpretation acquisition even though the two Modules use different operations of each other's Interfaces.

Acquisition must be able to return malformed model members as raw attributable content. Validity is not a prerequisite for diagnosing invalid content. Missing members or uncertain membership produce incomplete acquisition; raw syntax errors in obtained members are actionable content findings and leave their dependent interpretation unassessed. Preserve field-level known facts where unambiguous; do not fabricate a normalized valid model from malformed input.

Bind selected project/model, observed state, membership, member content, profile declaration and governing definitions. A declaration names both metamodel and representation profile and their applicable content, not just a mutable filename. Missing, ambiguous, conflicting, inaccessible or unsupported profile context leaves the corresponding interpretation unavailable. Never substitute the newest profile. Current authoring explicitly selects its target profile, while retained source interpretation keeps its original rules; selecting a target does not adopt it.

## Whole-model conformance request and checking

`check_model_conformance` takes the captured basis, declared rule-family selection, complete relevant membership or stated gaps, and optional prior/proposed state and decision inputs for transition checks. Include supplied review judgments only as separately attributable display inputs. Unknown request operations or rule-family selectors reject; a known declared rule that the engine cannot evaluate is an unsupported check. A value outside a declared entity vocabulary is invalid content, not an unsupported alternative to accept.

Build a deterministic inventory from the complete acquired membership. Check locally decidable rules first, then dependent consistency rules:

1. Decode each member using its selected representation and validate record shape, required fields, property names, types and closed values. Reject unknown values before any dependent consistency check can fall through to a known branch.
2. Index known identities with original record/path locations. Reuse FUNC-002 to diagnose absent and duplicate identities across distinct definitions, independently of display names and record kinds. Do not choose a duplicate as the reference target. Check profile-declared derived naming and storage-containment agreement against the actual authoritative fields and paths.
3. Resolve typed references and authoritative relationships using unambiguous known endpoints. Diagnose unresolved or incompatible endpoints and competing authoritative/inverse representations. Reuse scoped relationship primitives, but do not treat a prior isolated edit check as whole-model proof.
4. Check profile-declared parent kinds, parent cardinalities and acyclicity over the complete relevant graph, including incoming edges and unchanged members. In the current REM profile, SRs have one IR parent, ARs one SR parent and each governed Scenario exactly one owning IR. Check ownership through its declared relationship, independently of filename or similar display labels. A cycle receives a finite witness path. A missing or ambiguous endpoint leaves affected dependent checks unassessed rather than generating a fabricated owner.
5. Evaluate explicitly declared lifecycle-transition predicates only against matching prior/proposed subject identities, both states and required decision input. Checking a current status value is not checking a transition. Missing prior state, decision provenance or supported predicate yields an unassessed/unsupported transition. The result may still contain valid independent state-only findings. No conformance result grants the decision or executes the transition.

A failing local field blocks only rules that require that field; independent checks may continue and retain their actual findings. Every skipped dependency is explicit. Stable ordering by subject, rule identity and location makes diagnostics reproducible; order never hides an adverse finding. Known violations survive interrupted or incomplete assessment elsewhere. Do not use a hidden record-count cutoff or report a canceled scan as conformance.

The requested scope may be narrower than all rules or all entities. Enumerate relevant context outside selected subjects where incoming constraints, reference resolution or uniqueness need it and label that context. Without complete required membership, absence cannot prove uniqueness or cardinality. A complete empty model can conform only if the selected profile permits it; emptiness and omitted scope remain explicit. No mechanical result infers that desired architecture or stakeholder obligations have been fully modeled.

## Results, diagnostics and supplied judgments

The result identifies exact state/profile and governing definitions, selected and actually evaluated rule families, checked subjects, acquisition/interpretation completeness, findings and unassessed scope. Each finding carries rule identity and source, subject identity where recoverable, original location/field, observed conflicting fact or missing value, deciding condition, relevant witness and a bounded correction explanation. When an entity identity cannot be read, retain its exact member location/content basis rather than invent an ID. These are result obligations, not a new transport schema.

Keep two dimensions separate: conformance observations (no known violation or known violations) and assessment completeness (complete, limited or unavailable, with reasons). A conformance conclusion requires complete acquisition/interpretation and evaluation of all applicable rules in its expressly stated scope with no violations or unresolved required checks. A narrower result names excluded rules and subjects. Unknown applicability, unsupported rules and interruption cannot produce an unqualified whole-model pass. Invalid request and failed execution remain distinct from an observed model violation.

Present a mechanical result and any supplied engineering judgment as separate attributed accounts. The mechanical account may establish only conformance to the named rules on the named state. It cannot establish approval, implementation, adequate reasoning, requirement satisfaction or permission. Two structurally valid models may have different engineering quality; the result preserves that review question.

A supplied judgment retains its purpose, actual assessor, exact subjects/basis, conclusion, limitations and observed applicability. When its subject/profile/scope differs from the conformance result, expose that mismatch; unknown comparison remains unknown. Do not refresh its applicability, merge it into a mechanical badge or discard unfavorable findings. MOD-007's assurance contract owns evidence sufficiency and accountable semantic judgment. This operation displays supplied assessment meaning; it does not call IF-010 or IF-014 across an undeclared boundary or make their decisions.

Likewise MOD-004/FUNC-010 and AR-060 own allocation analysis. A supplied allocation difference with no deciding rule remains an engineering-review need. It is neither a mechanical conflict nor a confirmed adequate allocation merely because other structural checks pass. IF-002's existing interpretation and relationship operations retain their own narrower meanings.

## Migration request and bounded mapping

`prepare_model_migration` receives an immutable source basis, exact source and target profiles, an explicit mapping with identity/content basis, intentional semantic-change declarations, and a declared consumer inventory with compatibility criteria and supplied observations. Source interpretation is performed under source rules; target validation uses target rules. Unknown profile support or ambiguous selection is reported, never guessed. This concerns engineering model representations, not operational SQLite/v3/v4 migration or workflow adoption.

The mapping is a finite ordered set of declarative transformations for supported profile adapters. Each rule specifies unambiguous source selectors, the source/target meaning it relates, target location/field/relationship representation, handling of relevant values and whether it preserves meaning or deliberately changes it. The supported primitive responsibilities are copying an identified value, renaming or relocating a represented field/member, translating an explicitly enumerated value, and reconstructing the profile-declared representation of an existing typed relationship or containment fact. Explicit additions, removals, identity changes, relation changes and defaults require a supplied intentional semantic-change declaration and basis. Unlisted source values never fall through to a default or get silently discarded.

Adapters implement these primitives under both identified profiles; a mapping cannot supply executable code, arbitrary filesystem/network access or undeclared callbacks. Unsupported transformations are reported with the affected scope. Overlapping selectors, conflicting target destinations, order-dependent overwrite and ambiguous value translation reject complete transformation. Rules must identify any intentional chained transformation explicitly; matching a rule against an accidentally modified intermediate source is not implicit pipeline behavior. Every rule reads the immutable source facts and writes a staged target; dependent target construction uses declared dependencies checked for cycles and missing inputs.

Before transformation, account for every included source member, governed field and authoritative relationship, including unchanged content. Record copy/transform/intentional removal/unmapped disposition. Unknown source content remains unresolved even if its bytes can be copied as opaque material; opaque copying alone cannot establish semantic preservation. Preserved supporting content retains attributable locations and links. Produce target definitions from identified source facts plus explicitly declared additions; never repair unsupported input opportunistically to obtain a passing target.

## Candidate identity, meaning and compatibility

Build in an isolated in-memory candidate, separate from source custody and current authoring selection. Candidate identity binds exact target membership/content, target profile and the source/mapping provenance. Return the candidate bytes or immutable content references together with its manifest; if a usable complete candidate cannot be returned, report only partial diagnostic material and no completed candidate. No target member may alias a mutable source buffer or be written through to an authoritative source location.

The transformation report relates source and target subjects, mapping rule and content identities, preserved entity IDs and relationship meaning, and every supplied intentional semantic change. Preserve stable IDs for representation-only changes. Changes to identities, parentage or typed endpoints cannot be disguised as filenames or labels. Compare normalized source and target authoritative facts under their respective profiles using the declared equivalence mapping. A representation-preservation claim requires complete mapped facts and justified equivalent meaning; a matching entity count or target schema pass is insufficient. Unsupported semantic equivalence remains a review need. The engine reports explicit change declarations; it cannot approve their engineering rationale.

Run whole-model target conformance over the exact staged candidate and complete target profile rules before returning its readiness account. A collision, unresolved reference, missing member, unsupported required rule or interrupted check keeps the candidate unresolved. Later candidate or mapping changes require a fresh candidate identity and affected assessments; do not attach old results to revised bytes.

For each declared current consumer, retain its identity/version, required compatibility conditions, exact candidate/profile basis, actual observation or accountable assessment, and supported/incompatible/unassessed result with rationale. Distinguish a supplied human compatibility judgment from an executed parser/test observation; neither is fabricated by candidate creation. Checks may be supplied by the participant from existing consumer-owned tools; this operation does not execute arbitrary consumer code. Admit support only for the exact candidate and criterion scope, with provenance and any required freshness; mismatched or missing support remains unassessed. Candidate preparation may first return a candidate for those checks, then reassess the exact unchanged candidate with supplied support.

The consumer inventory declares its completeness and selection rationale. Known omitted consumers, unknown inventory completeness or missing required checks prevent a general readiness claim. An explicitly complete empty inventory can be meaningful only with a justified no-consumer scope; empty input is not automatically complete. A scoped compatibility conclusion names exclusions. Relevant repository consumers can include authoring, model interpretation, relationship readers, schema checks and browser generation, but their presence is discovered from the declared project basis, not invented as a universal fixed list.

Report separately: transformation completion, semantic-preservation/intentional-change review needs, target conformance, per-consumer compatibility and overall readiness limits. A candidate is eligible for controlled-adoption consideration only when complete transformation, all required target checks, required mapping/semantic review and declared consumer compatibility have adequate support. This does not approve adoption or waive MOD-006 change authority. Outstanding required checks, ambiguous mapping or semantic gaps withhold readiness. Returning an unresolved candidate can still be useful for review; do not mislabel that as a completed migration.

## Failure, source preservation and realization

All migration preparation operates on immutable captured inputs and private target buffers. Failed, canceled or abandoned work cannot modify source content, historical profile definitions, current profile selection or retained Baselines. Discard only owned temporary candidate buffers. Report incomplete candidate scope and actual available artifacts; do not claim rollback of an adoption that this operation never performed. A lost response leaves candidate availability unknown to the caller; retrying preparation from identical immutable inputs is safe but grants no retention or adoption. A changed source selection requires a new request and report.

Persisting or adopting a candidate is a separate explicitly authorized workflow. Existing storage retention primitives do not imply an atomic whole-model profile migration; no adoption-ready runtime migration writer is claimed here. The candidate/report can be handed to the responsible maintainer without exposing internal IF-002 wholesale outside MOD-016. A future external command or adoption adapter must preserve these semantics under its own reviewed boundary. Initial supported profile pairs are those with explicitly qualified adapters and mappings; this design does not promise universal format conversion or current support for every retained profile.

The proposed shared local Rust model engine contains a MOD-003 acquisition coordinator, pure declared-profile decoder, rule dispatcher/identity and graph indexes, diagnostic builder, migration transformer and candidate/report assembler. MOD-001 retains immutable capture and filesystem custody; the pure IF-002 operations receive raw inputs and cannot recursively acquire them. Reuse the existing model interpreter and identity/relationship rule primitives rather than duplicate their definitions. Typed outcomes preserve known findings and missingness through the pipeline. Deterministic ordering and bounded finite input processing make repeated inspections reproducible; explicit cancellation/resource exhaustion still produce limited outcomes.

Development organization places these components alongside the existing proposed model interpretation and checking engine, with retained profile adapters and mapping definitions as versioned resources. The same pure conformance component checks an acquired source or a staged target without granting either approval. Separation of read/capture, pure transformation and later retention prevents an incidental diagnostic or failed mapping from becoming a model write. No new database, persistent inverse graph, D2 dependency, network service or execution scheduler is needed. Runtime adapters, numerical capacity qualification and delivery proof remain separate.

Physical execution is one local engine invocation over immutable source content and private memory; the original model and historical profile resources remain with their storage owner. Findings and candidate/report artifacts are returned to the requester. A later persisted artifact must use an explicit custody contract, never an implicit overwrite. The [responsibility and migration diagrams](README.md#conformance-responsibilities) explain Logical and Process composition. These paragraphs own the Development and Physical choices.

## Scenario and criterion inspection

SCN-011 uses the selected state's original rules or reports their unavailability. SCN-012 diagnoses model defects and unassessed transitions without calling a partial scan valid. SCN-013 juxtaposes mechanical facts and supplied accountable judgments without merging their meaning. SCN-014 returns an attributable candidate with transformation, target and consumer limits while preserving the source. These are walkthroughs of the governed Scenarios, not replacements for their black-box definitions.

| Basis | Design inspection cases and expected distinctions |
| --- | --- |
| SR-012 C1–4; AR-010 | Two states with different retained profiles; missing/ambiguous/unsupported definitions; explicitly selected current authoring target. Verify governing rules accompany results, no latest-profile substitution and no implicit adoption. |
| SR-013 C1 | Unknown property/value, missing field, malformed record. Identify subject/location and deciding rule before dependent consistency; independent findings survive. |
| SR-013 C2–3 | Duplicate IDs with equal/different labels; wrong derived path; wrong/multiple requirement parent; finite cycle; missing/wrong-kind endpoint; zero/two owning IRs for a Scenario. Check authoritative facts and incoming scope, never filename similarity. |
| SR-013 C4–5 | Transition without prior state or decision; unsupported predicate; narrowed rule scope; interrupted scan with known violations. Keep state-only observations, unsupported/unassessed scope and whole-model conclusions separate. |
| SR-014 C1–4 | Structural pass with inadequate reasoning; separately supplied stale/current judgment; allocation difference with no deciding rule. Preserve exact mechanical scope and actual review attribution without asserting approval, implementation or satisfaction. |
| SR-015 C1–2 | Complete explicit representation mapping; intentional semantic change; identity/edge preservation ledger. Return exact candidate/source/profile/mapping basis and meaningful change disclosure. |
| SR-015 C3–4 | Unmapped/opaque source; overlapping rules; target collision; failed transformation; stale or absent consumer observation; unknown consumer inventory. Preserve diagnostics and withhold unsupported readiness. |
| SR-015 C5 | Cancel, fail or abandon candidate; source changes after capture; retry after lost response. Source bytes, retained historical meaning and current profile selection remain unchanged. |

These cases define Design acceptance intent. Implementation must later demonstrate actual decoding, graph diagnostics, source preservation and supported transformation/consumer outcomes; structural schema tests alone do not supply that proof.
