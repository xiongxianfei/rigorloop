# Requirement delivery assessment format

This is the G0 architecture contract for explicit IR/SR/AR Implementation and Verification disclosure under MOD-004. The [evaluation design](requirement-evaluation.md) owns assessment meaning; [the Requirements tree](requirement-tree.md#current-repository-design-browser-scope) owns the supported external AR-only version 1. The [version 2 JSON Schema](../../../../../support/requirement-delivery-v2.schema.json) defines exact structural fields. This document supplies mandatory semantic checks and the matched producer, importer and reader contract. Both are required for implementation; a schema pass alone is insufficient.

The accepted IR-002/SR-008/009/085/086 basis supports this refinement through existing FUNC-007/009/080/081 and MOD-004. No new requirement, Function, Module, operational record type or public command is introduced. MOD-007 retains judgment and applicability policy; MOD-011 retains operational records; explicit caller selection crosses into MOD-004 as disclosed bytes. Existing IF-001/002 supply model content and interpretation. No live store access is added to model capture, the generator or the offline reader.

## Version and authority decisions

Use delivery `format_version: 2` with `assessments` and `resolutions`. Version 1 remains a supported external AR-only contract with its original admission and meaning; do not rewrite retained version 1 bytes or judgments. Reject other versions and do not silently down-convert version 2. The separate `--design-reviews` input and its version 2 Design companion remain authoritative for displayed Design judgments and allocation dispositions. A delivery version number is not a Design version number; the two envelopes are never interchangeable.

Keep `--assessments PATH`, `--clear-assessments`, explicit reuse of `assessment-snapshot.data`, and offline embedding. No selection means Unknown / Not assessed. The implementation of this target must accept both supported delivery versions through one normalized internal projection and one reader, with version-specific admission only at the external boundary. It must not maintain two internal stores or dual-write obsolete formats. The repository renderer accepts both versions; format support does not grant an assessment or adopt a customer generator.

An accountable reporter prepares implementation observations in existing Evidence. A responsible verifier records actual scoped Verification, including inconclusive or failed conclusions. Approved design-purpose Review supplies an IR's assessed stakeholder-outcome basis. Source references carry the exact retained supporting payload identity, not the hash of a mutable record container. The producer selects and reads those records and attachments through the supported CLI, checks actual attribution/applicability and explicitly authorizes disclosure of the selected content. MOD-004 transports supplied judgments; it does not authenticate actors, perform review or create implementation/verification conclusions.

### Mapping existing operational records

The producer uses the executing CLI's supported `rigorloop-records-v4` contract; it does not extend SQLite or invent a Verification result enum. Retained reporter/verifier-authored attachments may supply the criterion/outcome detail and sanitized disclosure that the generic records do not encode as dedicated fields. Bind the source reference to those exact retained supporting bytes and check that their actor, scope and conclusion agree with the selected record. Missing or inconsistent detail blocks preparation of the affected positive claim; it is not filled from code or test counts.

| Existing source observation | Permitted disclosure |
| --- | --- |
| Evidence result Passed/Failed/Inconclusive | Preserve its procedure result as an observation. An implementation state requires a separate explicit reporter-authored account in that Evidence/supporting payload; never map Evidence Passed to Implemented or Failed to Not started. If no implementation account exists, use `implementation: null`. |
| Verification outcome `success`, support Current | Report Passed only if the verifier actually assessed every required criterion/outcome of this exact requirement and all completeness rules hold. Both a scoped and a final Verification need that coverage; neither scope label alone qualifies the requirement. A narrower successful test/assessment supplies evidence, not a fabricated whole-requirement pass. |
| Verification outcome `failed`, support Current | Report Failed for an explicitly identified applicable failed criterion/outcome in this requirement. A failure outside its scope cannot be reassigned to it. Preserve adverse observations and their original subject identities. |
| Verification outcome `inconclusive`, support Current | Report Not assessed with its actual limitations and covered/uncovered rows. If the record simultaneously asserts an applicable failed criterion, return that inconsistency to the verifier; do not silently discard the failure or recast the conclusion. |
| Verification `support_state: needs-reassessment` | Carry noncurrent supplied applicability regardless of source hashes; preserve the original outcome as historical and show Needs reassessment. Only an explicit accountable renewed assessment may restore reliance. |
| Approved design-purpose Review of IR outcomes | Retain its actual reviewed basis/subjects and exact original support identity. An unrelated approved Review or any non-approved judgment cannot establish this basis. |

For positive reliance, the producer also reconciles currently relevant unresolved concerns in the selected records and their support, including adverse observations arising after an earlier report. It must not omit them merely to make a later export positive. This is scoped accountable evidence selection, not automatic store-wide discovery. The importer can check the disclosed contract and identities; it cannot authenticate unseen records or recover deliberately omitted facts.

## Exact export structure

All schema object fields are required; nullable fields explicitly admit JSON `null`. Omission is invalid. Empty arrays mean the named collection is empty, never that validation may skip required coverage. Unknown object fields, kinds, versions, states and duplicate JSON keys reject before consistency checks. The captured definition's `content` is an exact UTF-8 JSON string, not another delivery-schema object. Its own duplicate keys and requirement identity/type must be checked separately. Calendar timestamps must be real UTC `YYYY-MM-DDTHH:MM:SSZ` values; a matching regular expression alone is insufficient.

| Object | Fields and meaning |
| --- | --- |
| Envelope | `format_version` is integer 2; `assessments` selects zero or more accounts; `resolutions` selects explicit recorded decisions about competing claims. Empty arrays clear the delivery selection without clearing Design. |
| Assessment | `requirement`, `kind`, `definition`, `scope`, `outcome_basis`, `implementation`, `verification`. `kind` is exactly `initial-requirement`, `system-requirement` or `allocated-requirement`, agreeing with the ID and captured/current model type. Multiple accounts for one requirement may preserve history or conflict; exact duplicate accounts reject. |
| Definition | `path`, `identity`, `content`. Hash the original decoded content bytes. They must decode to the selected ID/kind. The current model must contain that same ID; a retired ID cannot create a new tree node. Its account stays in operational history until a separately supported historical-model selection exists. |
| Claim | `identity`, `state`, `actor`, `reported_at`, `source`, `summary`, `limitations`, `subjects`, `applicability`, `criteria`, `membership`, `child_support`, `nonreliance`, `design_support`, `concerns`. Implementation and Verification each have their own claim or `null`; `null` means no supplied assessment, not Not started or Failed. |
| Source reference | `change`, `kind`, `id`, `identity`. Kind is `evidence`, `review` or `verification`. Identity binds an exact retained source payload selected by the producer. It is not a fetch URL or proof that the reader accessed private storage. Implementation claim sources are Evidence; Verification claim sources are Verification; outcome-basis review sources are Review. |
| Subject | Public repository-relative `path` and exact SHA-256 `identity`. Repeated paths in one subject list reject. Claimed material basis is independent for each claim; the importer compares the declared subjects and does not scan for undeclared evidence. |
| Applicability | `state` is `current`, `needs-reassessment` or `not-applicable`, with `explanation`. It is the responsible reporter's supplied disposition. Mechanical byte matches may further restrict currentness but never promote a noncurrent disposition. |
| Criterion/outcome account | `key`, claim-specific `state`, `explanation`, `evidence`, `gaps`. Each evidence item supplies `source`, `summary`, `subjects`, `limitations`. These are disclosed observations and exact provenance, not executable links. Evidence subjects must appear with the same identities in the claim's material subjects. |
| Concern | `id`, `source`, `state`, `explanation`, nullable `disposition`. States are `open`, `deferred`, `resolved`; a resolved concern requires a disposition source and explanation, other states require `null`. IDs identify actual source findings/issues. Open or deferred relevant concerns withhold complete positive presentation. A deferral alone is not a waiver. |
| Membership | `identity` and sorted unique `children`, each with `requirement` and `definition_identity`. IR membership contains direct SRs; SR membership contains direct ARs; AR claims use `null`. This is an assessed captured set, not a second authored parent relationship. |
| Child contribution | `child_support` contains `requirement`, exact child `claim` identity, nonempty parent-unit `coverage`, and `explanation`. `nonreliance` contains direct child ID and an attributable explanation of why its account is not used. It does not remove a required parent outcome. |
| Design dependency | `design_support` contains requirement ID and exact selected Design account identity, using the existing Design account identity rule. This is explicit reliance, not a new Design judgment. An absent or changed relied-upon account restricts only the dependent delivery claim. |

Schema bounds are ceilings, not padding targets. ID strings and references must resolve uniquely within the selected envelope/companions where this contract requires a selected account. Record references are opaque attribution and are not resolved by the importer. A semantically valid reference to an unavailable private payload is not fabricated proof: the producer must disclose that evidence limitation and must not supply a complete positive claim on it.

## Complete criterion and outcome coverage

For an SR or AR, `outcome_basis` is `null`. Each nonnull claim has exactly one row for every captured `acceptance_criteria` entry: `C1` through `Cn`, in numeric order. Criterion text is taken from the exact captured definition, not supplied again by a claim. Missing, duplicate, additional or wrong-kind keys reject, including for Unknown and Not assessed accounts. Definitions that add, remove, reorder or change criteria invalidate the old claim's current applicability; preserve its original text and positions as historical. Do not align rows to a new definition by matching text or list position.

An IR has no canonical acceptance criteria. Its `outcome_basis` is either `null` with both claims `null`, or a complete reviewed basis containing `identity`, ordered `outcomes` and `review`. Outcomes use contiguous `O1` through `On`, each with `text` and nonempty exact source subjects. Review contains an approved design-purpose source, actor, time, scope, summary and material subjects. Every outcome source must be in that reviewed material basis, including the captured IR definition and relevant confirmed Feature/Scenario/SR sources. Review must explicitly establish coverage of the entire stakeholder need; child counts cannot do so. Claims cover every outcome exactly once. The reader labels them **Assessed stakeholder outcomes**, never IR acceptance criteria.

The reviewed outcome basis is self-contained in delivery version 2. Its review and sources remain attributable even when no Design companion is selected. It can be prepared from an existing approved outcome review without reinterpreting the obligation; the producer preserves that review's exact source identity and inspected outcomes. Changes to basis contents, review support or sources require explicit reassessment. They affect both IR claims because both assert those outcomes; unrelated Design display changes do not.

Implementation states are `unknown`, `not-started`, `partial`, `implemented`. Unknown rows must all be Unknown; Not started rows must all be Not started. Partial requires nonempty material subjects, an identified Partial/Implemented contribution and named remaining gaps or limitations. Implemented requires every row Implemented with evidence, nonempty material subjects, and no criterion gaps or whole-claim limitations. Code existence, allocation links and a completed Change cannot satisfy these rules.

Verification states are `not-assessed`, `failed`, `passed`, `needs-reassessment`. Not assessed must not hide a Failed row; Failed requires an identified Failed row with evidence. Passed requires every row Passed with evidence, nonempty material subjects, and no criterion gaps or whole-claim limitations. Needs reassessment preserves the supplied prior/uncertain result and reasons without claiming current success. A current confirmed failed criterion cannot be hidden by assigning Needs reassessment to an otherwise applicable account; the verifier must report Failed or explicitly establish why that adverse observation is no longer applicable. Partial passing evidence may remain under Not assessed. Neither implementation nor verification state is computed from the other.

Observation-specific limitations remain visible even when other evidence closes that observation's limited scope. The responsible assessment must explain their combined coverage; a reader does not add partial observations into a pass. Supported environment and assessed subject boundaries remain explicit in `scope`; narrowing scope cannot exclude a required criterion while claiming the whole requirement Implemented or Passed.

## Identity and dependency rules

Every identity has the form `sha256:` followed by 64 lowercase hexadecimal digits. Definition and file identities hash actual bytes. Structured identities use UTF-8 encoding of JSON with lexicographically sorted object keys, unchanged array order, no insignificant whitespace, unescaped Unicode and no final newline. Strings use normal JSON escaping of quotes, backslashes and controls; do not normalize Unicode or normalize the content string's line endings. Reject unpaired surrogates, nonfinite numbers and numeric spellings/types outside the schema's integer fields. These rules match the repository's existing `design_identity` convention; no general cross-language numeric canonicalization is needed for this string/array/object and fixed-integer format.

Outcome-basis and membership identities hash their object with only its own `identity` omitted. A delivery claim identity hashes this exact wrapper:

```json
{
  "requirement": "SR-009",
  "kind": "system-requirement",
  "definition_path": "<exact captured repository-relative locator>",
  "definition_identity": "sha256:<captured-definition-digest>",
  "scope": "<exact assessment scope>",
  "outcome_basis_identity": null,
  "claim_kind": "verification",
  "claim": "<claim object with only its identity member omitted>"
}
```

The placeholders illustrate hashing inputs, not a valid selected account. Use the actual claim object and actual digest; IR wrappers contain their outcome-basis identity. The captured definition path is identity-bearing as well as its content digest. Resolve current definition placement by stable requirement ID; any path relocation requires reassessment even if bytes are unchanged, and the original path remains historical provenance. Old-path and current-path accounts therefore cannot coalesce under one claim identity. This excludes the neighboring delivery claim. A change to Verification evidence cannot stale Implementation merely because both occupy one assessment object. Claim-specific material subjects, membership, declared applicability, source and support all participate in that claim identity. Distinct claim identities with equal state labels are still distinct assessments.

Only direct requirement-child dependencies in the claim's captured membership are admitted, and a parent claim depends on the same kind of child claim. Validate the selected captured child account's ID, kind, definition identity and claim identity against that captured membership, independently of today's parent edge. IR→SR→AR is acyclic; invented children outside the captured membership, arbitrary cross-level, self, cycle, missing selected claim or wrong-kind captured references reject. A claimed child identity must be present in the selected envelope and bind the stated child and captured child definition. The producer must establish that the captured membership describes the assessed model; a checksum of an invented list does not establish true historical parentage. Current parentage is checked only for applicability after this admission. A child moved to another parent, or removed from this parent while still present in the current model, leaves valid original support readable as stale history. Deletion of the child's canonical ID is the separately unsupported current-model selection case described above: reject that export before output writes and preserve its operational history and prior artifact, rather than silently dropping a required dependency. Build claims leaf-first for hashing; compare applicability leaf-first after all admission checks. One child observation may contribute to several parent units, but coverage lists must contain unique actual parent keys. Child counts and support lists never manufacture a parent result.

Membership is mandatory for a parent Implemented/Passed claim and whenever child support or nonreliance is supplied; it may be `null` for a bounded noncomplete claim that declares no dependence on child composition. Every captured direct child must appear exactly once in support or nonreliance when membership is present. Zero children is an explicitly hashed empty membership, not vacuous support. A membership mismatch affects only claims that carry it. Compare IDs and definition identities against the complete captured current tree, not the filtered display. A new, removed, moved or changed child makes the affected completeness/reliance basis require reassessment.

If an explicitly relied-upon child claim changes, loses applicability, becomes unresolved/conflicting or has relevant adverse evidence, withhold the parent's current positive result. A child failure does not mechanically become a parent Failed judgment. Applicable adverse child claims remain visible even with nonreliance: display that attributable reason and require the responsible assessment to reconcile its relevance. Nonreliance cannot waive a required parent outcome or hide an adverse observation within the parent's claimed scope. Independent direct system evidence can support an SR without ARs and can support a parent that does not rely on child assessments.

## Conflicts, dispositions and history

After structural, identity and coverage admission, evaluate supplied applicability, current definition, outcome basis, material subjects, membership, Design dependencies and child support. Missing/changed material data is an applicability reason; an unsafe path or malformed assertion is an admission failure. A byte match establishes only mechanical agreement. The reporter's noncurrent disposition and unresolved relevant concerns still constrain the claim.

For candidate-set membership, first distinguish a basis-current claim from a claim eligible for positive presentation. An applicable failed claim or a basis-current claim with open/deferred concerns remains in the competing set. Its adverse state or concern constrains positive presentation; it must not be filtered out to make another Passed/Implemented claim the sole candidate. A concern is not itself a subject-hash mismatch or a supplied noncurrent disposition. Only actual stated/compared loss of basis removes a claim from the current candidate set, retaining it as history and preserving the producer's duty to reconcile still-relevant unresolved concerns.

For each requirement and claim kind, coalesce an identical claim identity encountered in otherwise distinct accounts. Zero applicable candidates means absence or historical-only presentation. One applicable candidate can supply its state subject to concerns and dependencies. More than one distinct applicable candidate is an ambiguous/conflicting selection, even if their state labels agree. Do not choose the newest timestamp, union criteria from competing accounts, or prefer a positive result. Show all competing accounts and withhold positive presentation until an applicable explicit resolution exists.

A resolution contains `requirement`, claim `kind`, `selected` claim identity, nonempty `superseded` entries, its actual source, actor, timestamp, explanation, material subjects and supplied applicability. Each superseded entry names the exact claim, its accountable disposition source, explanation and `addressed` tokens. Its source uses the same Evidence/Verification kind as the claim being resolved. Resolution selects an existing judgment; it cannot supply missing criteria, change its state or manufacture approval.

A current resolution must cover the complete applicable competing set exactly once: selected plus superseded identities, with no omitted competitor. Its material subjects must remain exact and its supplied applicability must be Current. Multiple different applicable resolutions conflict rather than resolving one another by time. For each superseded failed criterion, include `criterion:Cn` or `criterion:On`; for every open/deferred concern include `concern:<id>`. The cited dispositions must actually explain correction, inapplicability or another authorized resolution of those adverse facts. Absence of required adverse tokens, a new competing account, changed resolution basis or unresolved concern makes the resolution insufficient; retain it with the diagnostic and withhold positive selection. A nonempty reason string alone does not authorize waiving a requirement or closing an issue.

The producer obtains and checks the actual accountable dispositions under MOD-007 policy. The importer checks explicit attribution, full references and exact compared identities, but cannot authenticate a private decision or prove its adequacy. Original failed accounts and finding identities remain disclosed history when superseded. A fresh positive assessment without an adequate adverse disposition cannot erase an open failure. Unknown claim references, duplicate superseded references or a selected claim also listed as superseded are malformed and reject; structurally valid but stale/insufficient resolutions are retained as explanations, never silently accepted.

For stale or unresolved delivery support, display current Implementation Unknown or Verification Needs reassessment while preserving the original supplied state, actor, source, definition, criteria and cause in history. No selected account yields Implementation Unknown / Verification Not assessed instead. A known applicable Failed candidate is always identified in details and conflict explanation even when a conflicting selection prevents a single authoritative indicator. The offline reader describes its captured snapshot only; it cannot discover later changes.

## Design and allocation composition

Join the existing Design selection and normalized delivery projection by the current canonical requirement ID. Definition lifecycle, Design, Implementation and Verification retain their separate authorities. Do not add a Design field or an allocation authoring field to the delivery schema. An absent Design account leaves Design Not reviewed and allocation Review needed; it does not automatically invalidate independently supported delivery claims.

An SR's allocation remains the existing Design account's `allocation` (`state`, `explanation`), captured `ar_children`, exact definition and material subjects, actor/time and actual `review` reference. Its currentness follows the existing Design projector. Compare captured membership against the complete current AR set; missing/stale support displays Review needed with original history. Only that reviewed account can supply No further AR needed. No AR declared remains a separate structural fact, and neither label supplies implementation evidence. A delivery claim that actually relies on a Design judgment lists its exact Design account in `design_support`; absence/change then restricts that claim. No undeclared reliance is synthesized merely because the badges share a row.

For IRs, displayed Design outcomes and delivery outcomes may have different reviewed bases. Label each basis and scope separately; never align them solely by `O1` or copy a Design pass into Verification. A producer should reuse the same applicable reviewed basis when it actually supports both. Its exact retained source review and outcome contents must still be identified, rather than assuming the current displayed Design account is the historical review.

## Producer, importer and reader

The sanitized export producer is a caller-side preparation step over explicitly selected supported operational records and retained attachments. It is not a new live record discovery service or an additional status-editing command. It verifies source attribution, exact source payloads, complete captured definition/outcome coverage, accountable concerns/dispositions and sufficient declared material dependencies, then produces the versioned document for disclosure. A private report may contain more evidence than its public summary; retain the exact disclosed observations and source identity without copying sensitive content into a website. The responsible assessor, not serialization, decides evidence adequacy.

The repository importer remains `scripts/lib/rem_browser_assessments.py`, composed by `scripts/lib/rem_architecture_browser.py` and `scripts/render-rem-architecture-browser.py`. The repository implementation uses the schema as the structural contract and the semantic stages here; it must not select values by guessing from current Python behavior. The existing reader resources consume only the normalized projection. A future packaged Node/Rust generator can implement this same contract only through its separately qualified shared browser-data/candidate design; this G0 does not add a second customer generator or support claim.

The [owning Process diagram](README.md#delivery-assessment-selection) shows these boundaries in the architecture browser.


The normalized in-memory map has one entry per selected current model requirement. Each entry has exactly `requirement`, `kind`, `implementation`, `verification`. Each indicator has `state`, `reason_codes`, `explanation`, nullable `selected`, and `history`. `selected` is one normalized report or `null`; history is the full ordered list of remaining reports with their original meaning. An unresolved conflict has `selected: null`. A stale single report is in history. The existing separately normalized Design map supplies Design/allocation and does not become another delivery field.

A normalized report has exactly `identity`, `source_format`, `definition`, `scope`, `actor`, `reported_at`, `state`, `summary`, `limitations`, `subjects`, nullable `source`, nullable `legacy_record`, `criteria`, nullable `outcome_basis`, nullable `membership`, `child_support`, `nonreliance`, `design_support`, `concerns`, `applicability`, `reason_codes`, and `dispositions`. Criteria have `key`, `text`, `state`, `explanation`, `evidence`, `gaps`. Version 2 fields preserve their admitted meanings; text comes from the captured criterion/outcome basis. `dispositions` is an array of objects with exactly `resolution` (the original admitted resolution), `status` (`current`, `insufficient` or `stale`), `reason_codes` and `explanation`. Include each resolution that names this report as selected or superseded, retaining inadequate or stale attempts without changing the original object. No source field is replaced with a current hash.

Normalized `reason_codes` is a unique ordered array using only: `no-account`, `reported-noncurrent`, `definition-changed`, `outcome-basis-changed`, `subject-unavailable`, `subject-changed`, `membership-changed`, `design-support-unavailable`, `child-support-unavailable`, `child-support-adverse`, `open-concern`, `conflicting-claims`, `resolution-unavailable`, `superseded`. Use this declared order when multiple causes apply. Explanations identify the affected paths/claim/concern and preserve scope without exposing private source content. An empty array means no restriction was found, not that the importer independently approved the claim.

### Version 1 normalization

Validate version 1 under the existing AR contract without imposing new version 2 fields or mandatory provenance. Preserve its original frozen bytes and present its scope and limitations. Convert one-based criterion numbers to `C1…Cn` and take text from the captured definition. For each claim, preserve actor, time, state, summary, limitations and material subjects; keep the original `{change,evidence}` as `legacy_record` and set `source: null`. Do not invent a Verification record, outcome review, allocation disposition, child reliance or declared contemporary approval.

A legacy normalized identity hashes `{source_format:1, requirement, definition_path, definition_identity, scope, claim_kind, record, claim, criteria}` using the structured identity rule. `claim` is the original claim object; `criteria` contains only its numeric key, that claim's state, and original shared evidence/gaps. Exclude the neighboring claim's states/subjects. Plain legacy evidence strings normalize into evidence objects with `source: null`, their text as `summary`, and empty subjects/limitations; this nullable source is internal legacy representation only, never admitted in version 2. Criterion explanation is the literal `Legacy version 1 criterion account.` The remaining new dependency collections are empty, outcome basis/membership are null, and concerns/dispositions are empty. `applicability` carries the literal explanation `Legacy version 1 account; currentness is bounded by its original admission and material comparisons.` with state Current before those comparisons. This is compatibility interpretation, not a claim of authenticated legacy approval.

The v1 empty envelope remains the explicit clear format; new v2 exports may also be empty. Do not emit normalized projection as a newly authored v2 export or convert an old Evidence reference into Verification. A version 1 companion is reused byte-for-byte under its current serialization contract; the new reader only replaces its internal interpretation. Design remains separately selected, so absence of Design still reads Not reviewed and an independently supplied applicable Design account still displays its actual judgment.

## Admission, bounds and failure preservation

Perform these stages in order before publishing any output:

1. Read at most 1 MiB plus one byte of delivery input; reject excess before decoding. Decode strict UTF-8, reject duplicate keys, then validate all closed schema structure/vocabulary before relational checks. Design's separate 4 MiB limit does not enlarge this delivery limit.
2. Validate safe paths, record syntax, real timestamps, exact captured definition content/identity/type, structured identities, unique lists and complete criterion/outcome coverage. Resolve all declared account/child/Design references; malformed or wrong-kind references reject. A missing selected Design dependency is an applicability reason, not invented support.
3. Compare the current model and each claim's material basis against one captured input set. Read each distinct subject once, preserving exact bytes/identity; a later source change detected before publication stops the attempt and requires a fresh capture. Do not mix model/subject generations. Resolve applicability, concerns and full competing-set dispositions, then parent dependencies leaf-first. Preserve all nonpositive causes and original reports.
4. Prepare the full normalized projection, HTML escaping and candidate output. Serialize a v2 companion as sorted-key compact UTF-8 JSON plus one newline, preserving every original decoded definition string and array order. Check both selected input and serialized companion against 1 MiB. Reject an oversized complete selection; never truncate subjects, criteria, concerns, history or child support to fit. Check normalized projection against 4 MiB of compact JSON before embedding; this internal expansion bound is separate from the unchanged input/companion cap.
5. Publish only under the existing generated-output replacement contract after complete candidate admission. Invalid selection, unavailable required capture, cancellation or resource exhaustion before publication preserves the prior selected companion and index. This format does not change the owner's existing commitment/recovery semantics or promise multi-file atomic rollback.

The structural schema additionally limits accounts and resolutions to 256 each, collections to their stated bounds, text to 16,384 characters, captured definition content to 262,144 characters, paths to 1,024 characters and depth to the format's finite nesting. Reject input JSON nesting deeper than 32 containers before constructing recursive data, including the captured definition. Bound distinct material file reads at 1,024, with 16 MiB per file and 128 MiB total; these are v2 admission budgets, not new supported model limits. Resource excess rejects before writes and identifies the exceeded bound. Existing v1 admission does not silently acquire these new per-collection or material-read restrictions. The caller can choose a smaller coherent selection but cannot omit support required by a selected claim.

Public subject paths use canonical relative POSIX spelling, with no absolute path, drive/URI colon, backslash, control character, `.`/`..`, empty segment or hidden component. Resolve without escaping the project or entering hidden operational storage, generated browser output or any selected output root through symlinks. Apply the same rule to definition paths and all evidence/review/claim/resolution subjects. Missing safe material files yield unavailable support; unsafe paths reject the export. Do not read arbitrary record locators or evidence text as paths. Record IDs, hashes and prose never initiate network requests, include local absolute paths or execute markup; render prose as text, using only existing validated model navigation links. Caller-authorized disclosure remains necessary because a schema cannot reliably identify private information hidden inside ordinary prose.

## Design acceptance and subsequent delivery

| Distinct situation | Required observation and independent oracle |
| --- | --- |
| Valid AR/SR and reviewed IR account | Every exact captured criterion/outcome appears with its own claim, source and limitation; compare to independently specified definition/basis, not renderer-derived expected values. |
| Unknown field/version/kind/state, malformed time/path/hash or duplicate key | The intended admission error occurs before any companion/index replacement; compare prior bytes, not only exit status. |
| Missing/duplicate/reordered coverage and missing reviewed IR basis | Incomplete claims reject; absent IR basis produces no claim and honest absence; no fake canonical criteria or vacuous pass. |
| Only Implementation material changes | Its result loses currentness while independently supported Verification remains as supplied, unless Verification explicitly declares that material reliance; mirror the case for Verification-only changes. |
| Unchanged bytes but reporter marks noncurrent or a concern remains open | Hash matches cannot restore a complete positive state; preserve disposition and concern identities. |
| Definition relocation with unchanged content | Old/current locators produce distinct claim identities; stable-ID comparison retains the old path and requires reassessment, never coalescing it into current success. |
| Child reparenting versus invented support | Admit internally consistent captured parent/child support, then mark current membership mismatch stale; reject a purported child outside captured membership. A deleted canonical child ID remains an explicit unsupported-selection rejection. |
| Changed definition, parent membership, outcome review or relied-on child | The affected exact dependency requires reassessment; independent neighboring claims survive; child failure never automatically decides the parent's judgment. |
| Current Passed claim competes with a current Failed/open-concern claim | Keep both in the candidate set; show conflict and adverse detail until a complete accountable resolution addresses the failure/concern. Filtering out the adverse candidate must not expose a sole Passed result. |
| Existing Verification is inconclusive or has noncurrent support | Inconclusive remains Not assessed; noncurrent support remains Needs reassessment despite exact hashes. Evidence Passed alone never supplies Implementation Implemented. |
| Competing claims and adverse history | No timestamp winner; a complete current accountable resolution selects an existing claim, preserves original failures and dispositions, and becomes insufficient when another competitor or unresolved adverse fact appears. |
| SR has no AR; all children pass; child fails outside declared reliance | Display structural absence, direct assessment and attributable nonreliance separately. No structural fact/count grants satisfaction or hides adverse support. |
| Legacy v1 alone or beside separately selected Design | Original AR scope/states and stale history survive without fabricated Verification/outcome/Design records; both delivery versions use one reader representation. |
| Unsafe disclosure, oversized input/normalized output or interrupted generation | Reject before publication and preserve prior output; no truncation, live record access or network fallback. |
| Copied page at desktop/narrow widths and keyboard-only input | Separate labeled indicators, history, criteria, conflicts, filters and full child counts remain readable offline in the existing system tree. |

Schema inspection and synthetic contract examples are structural or capability evidence, never actual SR/AR delivery accounts. The repository realization lives in `scripts/lib/rem_browser_assessments.py`, the existing renderer and reader resources, using the repository's existing JSON Schema validation dependency.
