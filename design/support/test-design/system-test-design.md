# System test design

This is the single test design for RigorLoop. It describes the system outcomes, significant failure scenarios, expected observations. Module contracts own required behavior; they do not maintain separate test sections or case catalogs. [System](../../architecture/composition.md#requirements) owns TEST-SR-01–23 and the shared [test-quality rules](rules.md). [Validation](../validation.md) owns implementation mappings, commands, execution and current coverage gaps; actual results and review judgments belong to Change records.

## Core scenarios

Use fresh temporary stores, Git repositories, destinations and archives. Invoke the real boundary being claimed; compare stored or installed bytes with independent expectations. Keep an ordered interruption/retry within one scenario. External publication providers may be controlled fixtures; actual public service behavior remains a release-time observation.

| Outcome and requirement owner | Conditions and independently expected observations |
| --- | --- |
| Valid completion — [Workflow][workflow], [Assessment][assessment] | Owner-selected requirements/design can complete without intermediate approvals. Missing independent whole-change approval, self-approval or missing Verify blocks completion. Changed support requires renewed Verify; adverse relied-on review and unresolved advisory findings remain visible obligations. |
| Durable, atomic changes — [CLI][cli], [Records][records] | Create work, resume in another process and observe the same records. Invalid fields/references, duplicate fields, unknown values and stale update intent reject without partial state. Interrupt persistence before and after commitment: report rollback or uncertainty truthfully, then inspect actual state. |
| Protected storage — [Records][records] | Opening corrupt storage fails without replacing it with an empty store. Symlinked store paths and storage auxiliary files reject without touching another destination. |
| Recoverable state — [Records][records] | Backup and restore preserve selected records and payloads. Reject corrupt/unknown bundles, occupied destinations and stale expectations. Interrupt replacement: keep work fenced; explicit finish uses the validated candidate, while rollback restores prior bytes and rejects a stale recovery observation. |
| Safe installation — [Installation][installation] | Install into a clean destination. Existing content, symlinks, unsafe paths or retention locations reject with user files preserved. A partial publication reports completed, failed and untouched units; retry preserves conflicts and explicit force performs the intended recovery. |
| Complete usable artifacts — [Packaging][packaging], [Installation][installation] | Compare both adapter archives against independently enumerated authored resources and expected transformed bytes. Inspect the actual npm tarball for required runtime content and excluded files. Run its installed CLI and initialize both targets; observe conflict/force behavior, unsafe-path rejection, a workflow transition and absence of runtime-state pollution. |
| Usable skill resources — [Skill procedures][skill] | Validate canonical skills. Starting from a valid copied skill, delete a declared resource: reject with the missing-resource diagnostic and do not recreate it. |

## Release scenarios

| Outcome and requirement owner | Conditions and independently expected observations |
| --- | --- |
| Exact publication authority — [Release][release], especially REL-SR-08/12/23 | Matching lightweight and annotated tags resolve to the trusted commit; mismatched tag identity rejects. Bind workflow authority to the exact retained candidate. Unknown authority values reject before consistency checks; unsupported triggers and a different initiating run cannot publish. |
| Honest publication and retry — [Release][release], especially REL-SR-10/14/24 | Successful execution persists observations; a duplicate start never republishes. Failed public smoke preserves publication facts and retry only observes. Tampered candidate bytes or a cancelled run cause no external writes. |

Release qualification must establish actual candidate identity and public installation observations. Simulated providers cannot establish public availability. Passing checks grant no publication authority and cannot waive required preflight outcomes.

## Integrated design and handoff assessment

For changes to authoring, workflow guidance or cross-Module cooperation, use an independent walkthrough of the actual affected definitions and outputs. This is a method for the applicable review, not an additional approval stage or an automatically passing test.

1. Start with a concrete request and its selected requirements, design, proof allocation and handoff. A useful counterexample is an all-or-nothing batch import: compare a coherent design with one permitting partial writes, and separately with one claiming a parser test proves atomic persistence. Expect the reviewer to identify the weakened obligation or insufficient observation and return it to the responsible owner.
2. Trace the selected requirement through logical behavior, Module/Interface allocation and planned evidence. Regroup work or move an artifact: requirement identity and meaning survive, current consumers resolve, and historical approval retains its original subjects. Lasting test intent remains readable here without the plan or private results.
3. Challenge scope and authority: a direct Plan correction must not authorize implementation or publication; discovery/research/learning supplies inputs rather than owner decisions; authored or saved work is not independent approval. Missing required basis blocks dependent work, while authorized independent work can continue. Changed basis and uncertain recording outcomes require inspection and appropriate reassessment rather than invented success.
4. Inspect the exact delivered skills/resources and handoff. A project with sufficient local input can produce a portable scoped result without internal RigorLoop files or a database; an ambiguous target blocks dependent action. Late recording, privilege or scope triggers pause only affected work until transitive resources, compatible versions and authority are settled. Untriggered resource absence does not block portable work. Obtain full subjects when summaries are insufficient, reject unknown vocabulary and exclude unrelated private inputs. Saved, conflict, busy and uncertain recording outcomes remain distinct; inspect before reconciliation, honor existing standing grants and reassess expanded scope. Review claims identify actual subjects and limits; external PR/release actions need their applicable authority. Vision/README agreement, foundation selection, repository observations and durable lessons require actual-subject semantic assessment when affected.

Exercise actual generated skills with the packed CLI: resources and documented command/response shapes agree. A retired command, incompatible response, stale writer or conflict cannot be hidden by package-content success. Public identity/availability requires actual release observations. Record the actual walkthrough, counterexample and outcome when performed; an authored procedure is not execution evidence.

## Additional integrated scenarios

These scenarios describe conditions and required observations across responsibilities. Derive expectations independently from the governing contracts. Their presence here does not claim implementation or successful execution.

| Outcome and governing basis | Representative conditions and expected observations |
| --- | --- |
| Resumable authorized work — SCN-023/075–081; SR-006/007/027–029/079–082 | A new actor with no chat reads selected basis, work, issues and review standing; a planned check remains unrun. Large context or changed record identity needs complete bounded selectors, not truncation. Revocation, nondelegable decisions, scope expansion and higher-authority conflict withhold only affected actions; restored/historical accounts renew no authority. Continue an authorized next milestone without another approval; failed checks, unknown authority or missing evidence constrain the affected action. Evidence replacement cannot erase another failure or an omitted finding. Harmless edits and collection retries preserve appropriately scoped support; material changes require reassessment within the same gate, and replacing a Review cannot silently renew Verify. |
| Coherent adoption — SCN-082; SR-023/024/055/083 | Distinguish inspected absence of earlier work from an unreadable store; empty target storage proves neither. Activation needs current authority and compatible selected records/package. Unavailable, failed or uncertain necessary migration and partial installation leave affected activation blocked. Successful migration preserves original identities and unselected work; a competing actor invalidates stale activation. Successful installation alone cannot create adoption or project-wide completion. |
| Payload and historical-account preservation — SCN-023/045–047; SR-006/023/024/043–047 | Fail after payload copy but before record commit: the unused copy is not Evidence. Missing, changed, symlinked or occupied payload sources remain explicit; cleanup racing retention must preserve referenced bytes. Compact only obsolete detail: unresolved findings, selected assessment dependencies and completion-selected attachments survive. Closed completion stays historical after later source edits; changed retry Verification cannot masquerade as the original completion. |
| Bounded transactional interfaces — SR-040–047/074–077 | Two Changes sharing a local ID cannot cross-reference records. Preserve opaque revisions beyond JavaScript safe integers and reject old incarnations. Distinguish precommit rollback, committed-but-lost response and source drift after commit without replay or false rollback. Oversized mandatory receipts/dispositions reject before writes; optional omissions and aggregate overflow expose usable smaller selectors. A Change-only read must reveal unselected advisory findings. Reject caller-supplied SQL/callbacks and retired successor inputs without fallback. |
| Maintenance and acquired-runtime coherence — SR-043–047/074–077 | Snapshot and payload selection agree while competing recording/cleanup is excluded. Missing payload, cancellation or exhausted capacity leaves source/backups usable and no complete marker. Restore without a lost source only from validated retained scope; no usable backup means unavailable. Transfer to a matching empty checkout preserves source and association. Import maps every selected dependency, preserves originals/issues and rejects collisions, unsupported dependencies or source drift before activation. Wrong project, altered digest, escaping member and stale/foreign replacement state cannot activate. Access rechecks the fence after a paused lease race; stale recovery cannot overwrite later work. Qualify the actual acquired CLI on supported Node/platform candidates, including binding settings, migration availability and diagnostic separation. |
| Explicit obsolete-skill replacement — SCN-063 and [Installation][installation] | Default or force alone cannot infer retirement. An authorized fixed profile selects only its declared old units under one root. Reject unknown/malformed descriptors, wrong target, altered archive or missing transitive resources before writes. Preserve original bytes outside discovery and unrelated paths; ancestor/path races, partial detachment/publication and lost output retain truthful effects. Retry does not infer adoption. |
| Customer browser and projection — SR-084–088; AR-043–051 | From an independently specified sparse model, retain exact identity, ownership, proposed/observed qualification and honest missing detail across all five views without fabricated project capabilities. Parent/child/root navigation preserves view and scope; command-to-responsibility/rationale links confer no approval. Reader walkthroughs must assess information hierarchy, keyboard/narrow layouts and unavailable deep links. Invalid or changed input preserves prior output. Copy output away from source/generator and disable network: required content/navigation still works. Exercise hostile text, competing writers, corrupt/unowned destinations and failures before/after entry commit. Acquired packages need renderer resources and supported dependencies. Runtime topology derives only from authored participants/channels; duplicate qualified names and reordered sources preserve correct selection, and missing behavior never invents order. |
| Requirement-tree reading — [reading contract][requirement-tree] | Disabled views expose no route; enabled empty views stay honest; invalid flags/models reject. System-only scope, labeled architecture transitions and return state remain distinct. Shared targets and dual relations retain exact parentage, independent occurrences and visible paths without invented links/owners. Assessment status stays separate from definition lifecycle; absent, partial, stale or conflicting support cannot become a positive complete badge. Frozen selections remain reproducible without private records; clearing restores absence, changed criteria downgrade only affected claims, and invalid/unsafe input preserves output. Expansion terminates across graph cycles; search/deep-link/Back, selection/reveal, focus, keyboard/narrow layouts and copied offline reading preserve coherent navigation. |
| Model custody and authoring — SR-001–005 and MOD-002 | Independently specify identities, membership, bytes and five rationale fields; save, end the session and retrieve exact current content without private work history. Missing required context remains distinct from optional history. Contrast blank/duplicate IDs with equal names, moved subtrees, target collisions and incomplete inspection. Create/replace/remove relationships from either endpoint, including required parents, competing cardinality and unknown types. Changed bases, unsupported custody, interrupted writes and lost responses cannot establish coherent success or permit blind retry; unchanged references and original meaning survive. |
| Conformance and migration — SR-012–015 | Compare two retained profiles, unavailable rules and an explicit current target: no latest-profile substitution or implicit adoption. Unknown values, missing fields, identity/parent/cycle/endpoint defects retain exact diagnostics and independent findings; missing prior state, unsupported predicates and interrupted scans stay unassessed. Separate mechanical validity from accountable judgments. Transform a complete mapping, then inject opaque inputs, overlapping rules, collisions, missing consumer observations, source changes and cancellation: preserve original bytes/meaning and withhold unsupported readiness. |
| Baselines, transitions and retirement — SR-020–024 | Capture exact model/rule/assurance membership, include external-only references, then change current rules or lose a receipt: retain original meaning and expose unavailable scope. Compare rename, new identity, changed allocation, identical facts, ambiguity and a missing side without treating unknown as unchanged. Recover intact, corrupt and partially copied baselines into isolated destinations; reject implicit active-work overwrite. Contrast observed, proposed, interrupted and corrected transitions. Retirement preserves required originals, active consumers and still-relied-on failures; changed authority, missing dependencies or partial removal cannot produce complete safe retirement. Disposable unrelied-on detail may be removed under its governing policy. |
| Traversal, allocation and potential impact — SR-009–011 | Use an independently specified graph with a long chain, branches, reverse edges, cross-domain/self cycles and multiple starts. Preserve reachable identities, finite witnesses and authored provenance. Vary depth zero, equal/smaller caps, missing targets, mixed states, unknown types/directions, interruption and exhausted resources: bounded or incomplete results never imply unrestricted completeness. Compare missing owner, allowed deferral, unknown eligibility, differing owners with equality/ancestry/no deciding rule, and incomplete incoming inventory; known violations survive alongside gaps. Mixed-type/direction impact paths produce each non-seed candidate once with exact cause/witness; mismatched support rejects, seed-only completion differs from incomplete emptiness, and potential impact cannot alter assessments. |
| Assurance content and methodology — SR-025–029; REM guidance | Compare complete and incomplete methods, actual/unperformed/interrupted occurrences, execution failure versus adverse observations, and inaccessible attachments. Wrong revision/criterion/condition, missing basis, stale judgment, advisory scope, actor report versus exact comparison and contrary evidence retain explicit distinctions. A method, coverage table, exception or saved preparation never becomes proof, approval or permission. Preparation/save races and lost receipts require bounded reconciliation. Trace retired methodology commitments and rationale to current owners; use one-parent IR/SR/AR and owned Scenario examples, then unrun/stale evidence, unsupported intended use and a hidden concern. Inspect isolated packaged resources and current links as well as semantic usefulness. |
| Learning and improvement — SR-035–038; IR-007 | Use a synthetic topic, independent classifications/effect criteria, exact before/after guidance and two identified activities. Contrast recurring facts, unsupported causes, one supported high-consequence weakness and a local typo. Pending confirmation has no effect. Distinguish relevant/excluded/unavailable lessons and incomplete context. A proposal, rejected decision, scheduled route or acceptance without changed artifact cannot mean adoption. Compare no opportunity, missing observations, reproduction alone, recurrence/new burden and later success after an unassessed failure: retain mixed results and comparable scope. Changed version/context and competing or interrupted topic writes preserve originals, custody requirements and reassessment uncertainty. |
| Selected-subject history — SR-078 | Prepare two Changes with renamed/revised and unrelated same-name subjects, unmapped history and multi-subject reviews. Select only explicit project-qualified identities and literal recorded associations; preserve origins without guessing finding relevance. Distinguish complete no-match from absent/unsupported/compacted/corrupt scope. Repeat and continue pages, then alter token/filter/project/order, mutate/revert or restore state and exhaust generation: reject changed-state continuation. Missing storage, sidecar requirements and maintenance fences never cause lookup writes. Multibyte caps, oversized units, empty limited pages, unavailable detail and output failure expose exact incomplete scope without truncation. |
| Requirement delivery and evaluation — SR/AR/IR assessment contracts | Independently specify captured criteria, outcome basis and claim dependencies. Reject unknown/malformed/duplicate fields, incomplete coverage and unsafe/oversized input before output replacement. No reviewed IR basis, absent AR allocation or all passing children cannot invent parent success. Keep Implementation and Verification reliance independent; unchanged hashes cannot renew a reported stale claim or hide an open concern. Relocation, reparenting and changed definition/outcome/child support affect exact reliant claims while preserving historical paths and independent neighbors. Competing positive/adverse claims need an accountable complete resolution, never a timestamp winner or filtered-away failure. Legacy v1 retains original scope without fabricated new assessments. Offline filters show full distinct-child counts and readable labels/history/limitations. |

## Maintenance

Change this design when required behavior, significant risks, scenario conditions or expected observations change. Test renames, file moves, runner choices, implementation refactors and changing coverage status alone do not require a design edit. [Validation](../validation.md#current-coverage-allocation) owns current test mappings, commands and coverage gaps; Change records own actual results. Requirements remain in their owning contracts, with common test-quality methods in [rules.md](rules.md).
