# Published product coverage

This analysis connects RigorLoop's published product contracts to the REM requirement, system-design, and proposed architecture model.
It extends the original engineering-model scope; it does not replace the current contracts or claim that published tools implement the new REM record formats.
The [source register](sources.md#src-published-products) identifies authority and provenance.

## Scope and interpretation

The inspected numbered-obligation population is 130 requirements in six current source contracts at repository revision `5cf0c7b6`:

| Source contract | Inspected obligation population | Detailed authority retained |
| --- | ---: | --- |
| [CLI](../../docs/design/cli/cli.md) | 32 CLI-SR requirements | Public request/result contracts, command semantics, safe writes, recovery, diagnostics |
| [Record Format](../../docs/design/cli/records.md) | 14 RF-SR requirements | Operational record kinds, meanings, stored versions, identity and preservation |
| [Skill](../../docs/design/skill/skill.md) | 35 SKL-SR requirements | Common capability behavior, specialist ownership, portability, resources, published applicability |
| [Packaging](../../docs/design/engineering/packaging.md) | 13 DIST-SR requirements | Candidate production, faithful transformations, package contents, integrity and compatibility |
| [Installation](../../docs/design/cli/installation.md) | 10 DIST-SR requirements | Trusted acquisition, target writes, conflicts, replacement, diagnostics and recovery limits |
| [Release](../../docs/design/engineering/release/release.md) | 26 REL-SR requirements | Qualification, publication authority, public observations, uncertain outcomes and reporting |

The population is source-qualified: a requirement is identified by its owning path and existing ID, not by an unqualified number.
Each obligation below has an explicit analysis disposition. A proposed REM correspondence is not a claim that every detailed clause, example, interface version, or acceptance observation has migrated.
The Skill child Designs and the System composition contract remain named owners; their full clause populations are not included in the 130-row inventory.
No source requirement is retired by this analysis. Historical cleanup and bounded-pilot clauses remain attributable to their original source and applicability instead of being generalized into perpetual universal requirements.

“Represented” below means that new or existing REM definitions express the identified responsibility and its source basis. The retained source still owns details that the REM record does not reproduce.
“Related” is a contextual relationship, not equivalence. “Retained” means the current source remains necessary; it is not permission to omit the obligation from a later adoption.
The current implementation is not modified, and public registry state is not inspected.

The new IRs identify user needs. Features describe useful capabilities, Functions describe their logical behavior, and Module allocations propose accountable architectural responsibility.
An executable command, a skill package, an archive, and a release procedure are different realizations or delivery surfaces; none automatically becomes an IR, Feature, or Module merely because it exists as a file.
Shared authority, evidence, authoring, and learning Functions are reused without giving their SRs additional parents.
The table derives Function membership from each IR's own SR confirmations. The linked Feature definitions also include shared realizing Functions established by other IRs; their references remain authoritative for the full capability composition.

Public contract accountability is shown separately in the [Interface index](../architecture/interfaces/README.md): MOD-018 provides IF-004 and MOD-019 provides IF-006. The child Modules listed above retain their Function allocations: MOD-010 supplies command behavior, MOD-011 retains record publication/recovery, and MOD-014 supplies installation behavior. The [parent Interface ownership refinement](../../docs/changes/2026-09-26-rem-architecture-refinement/parent-interface-ownership.md) preserves the original six contracts, their consumers, and the existing requirement obligations.

The [parent-boundary contract analysis](../../docs/changes/2026-09-26-rem-architecture-refinement/boundary-contracts.md) adds bounded cooperation without changing those allocations. MOD-012 consumes MOD-017's IF-008 for the adopted model-authoring branch of SCN-053; other specialist activities retain their own procedures. MOD-015 consumes MOD-017's IF-009/IF-010 for the separate authority and evidence inputs in SCN-066, alongside the existing IF-005 artifact supply. MOD-015 still owns exact-candidate qualification, sealing, publication, and actual outcome reporting. Together with IF-007's selected-state inspection for Baseline analysis, the current model has ten Interfaces; these additions do not establish complete product architecture coverage.
