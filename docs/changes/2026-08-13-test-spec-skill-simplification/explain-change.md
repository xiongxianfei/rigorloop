# Why the Test-Spec Skill Changed

## Outcome

The `test-spec` package now gives portable proof design a shorter common path while retaining exact governed authoring, boundary-first proof, structural composition, and lifecycle safety. Both loaded procedural profiles and the complete package are smaller, and generated adapter resources remain byte-consistent with canonical sources.

## Behavior preserved

The skill still requires traceable proof for normative requirements, errors, compatibility, boundaries, examples, regressions, commands, milestones, gaps, and optional manual evidence. Governed authoring still ends at `review-required`; `test-spec-review` owns peer settlement, workflow owns later routing, and authoring cannot claim implementation, verification, branch, PR, release, deployment, or publication completion.

## Boundaries and risks

The new reference is conditional procedure within the same published skill package, not a new lifecycle owner. Missing, unreadable, stale, escaped, ambiguous, conflicting, or mixed-version resources stop before dependent interpretation or writes. Existing archive and clean-install checks cover Codex, Claude, and OpenCode. No target-agent runtime, sixth asset, manual-proof contract, tokenizer dependency, permanent simplicity validator, state schema, package transformation, or architecture decision was introduced.

## Validation basis

The milestone evidence records canonical validation, six focused tests, 330 broad tests with 16 skips, seven generated-skill tests, generated-output checks, boundary validation, adapter-distribution tests, direct v0.4.0 archive and clean-install validation, metadata and review validation, and diff checks. Final holistic code review is clean; final branch verification remains the next gate.
