# Governed PR readiness

Read this reference when the project has adopted the current operational workflow and the caller selects a Change. Read the packaged operational-recording reference before inspecting the handoff.

Match the selected Change, actual repository/remote/branch, refreshed base and full delivered diff. Inspect current independent whole-change Code Review and distinct successful final Verify, including their scope, current support and limitations. Read the accepted requirement/design basis, plan and selected supporting records when needed to judge readiness. A completed historical account does not establish current readiness for unrelated later edits.

A save, installed skill, clean advisory review or completed milestone does not approve the Change. Missing, conflicting or outdated support returns to its responsible owner. PR preparation does not write assessment judgments or use SQL, private record paths or storage recovery.

Classify any changes since the assessed basis by their meaning and effect on reliance. Pure operational recording of an existing conclusion does not automatically restart Code Review. Engineering changes, altered obligations or evidence that contradicts a relied-upon judgment require explicit applicability assessment and appropriate independent reassessment. Preserve the original scope of every conclusion; do not silently extend it to a new diff.

Prepare the PR title and body from the actual problem, delivered behavior, validation and material limitations. Check existing PR identity before creation. Push and PR submission require applicable user authorization; neither grants merge, release, force-push or branch-deletion authority. Report hosted CI success only after observing the hosted run. Use the project's separately authorized CI-repair scope if present; do not silently broaden it.
