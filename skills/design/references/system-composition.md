# Composition across model owners

Select the affected owner set and its relevant interactions. A system-level Design explains external actors/boundaries, the model inventory, responsibility relationships, significant dependencies, end-to-end behavior and genuinely system-wide quality/failure obligations. Reference component contracts; do not copy their requirements. A submodel is a coherent responsibility, not automatically one old file, feature, team or class.

Name one owner for each shared contract. Producers and consumers reference that owner and its stable identities. System is not a higher-priority document and cannot silently overrule a component or project governance. Unmigrated areas retain their declared source owners; inventory inclusion does not claim their consolidation or approval. An unknown owner is an explicit gap.

For a changed interface or shared assumption, identify affected producers/consumers, required reconciliation and justified unaffected paths. Examine data/authority transfer, compatibility, timing/retry, partial failure, recovery and prohibited side effects where material. A locally valid component can still compose incorrectly with an old consumer. Use representative integrated outcomes wherever local checks cannot establish the system property.

Review the changed models, relied-on examples and relevant interactions as an exact subject set. Readers and reviewers need not load every repository model. Existing CLI selection, identities and structural checks remain mechanical assistance, not a semantic dependency or readiness engine.

Hand Delivery stable local and integrated obligations with observable outcomes. Concrete proof allocation and implementation fixtures stay downstream; actual assessments/results remain with their existing owners. Preserve explicit current ownership during coexistence and assign genuinely deferred consolidation to a named later owner without deferring required present consumers.
