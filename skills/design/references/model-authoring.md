# Living-model authoring

Keep one current normative Design per coherent responsibility. Use `docs/design/M/M.md`, where directory and filename share stable model ID M; model-owned examples live under its `examples/` directory. An explicitly selected existing historical flat model may be revised in place under project authority; do not create a flat copy, silently relocate it or retarget an assessment. Model paths cannot point into examples or arbitrary extra normative nesting. Reject unsafe or ambiguous targets.

## Contract and structure

Explain goals, context, scope/non-goals, constraints, responsibility structure, runtime/operational and deployment boundaries, technical choices, quality, risks and necessary terminology to the depth needed for the claims. Cover invalid inputs, state/authority transitions, compatibility/migration, retries, concurrency, recovery, observability, security/privacy and accessibility where applicable. Explain material non-applicability instead of inventing components or metrics. Keep intended outcomes distinct from concrete downstream tests and mutable execution status.

Declare exactly once `Model validation contract: model-document-v1`. This document-format marker is independent of runtime record versions. Revise an older document marker only under the project's authoring authority; installing this skill does not authorize rewriting project models. The current validator rejects retired or unknown markers rather than selecting another runtime format. Use one level-two `Requirements` section with exactly `ID` and `Required behavior` columns. IDs are unique, nonempty, start with a letter and contain only letters, digits and hyphens. Normative text is nonempty.

Use one level-three `Boundary scan and acceptance scenarios` section with exactly `Dimension`, `Requirement basis` and `Distinct outcome to demonstrate` columns. Include each dimension once: Input domain; State/lifecycle; Identity/authority; Composition/path; Temporal/retry; Failure/recovery; Compatibility/migration; External/environment. Applicable rows cite unique model-local requirement IDs separated by comma and one space and give an observable outcome. Non-applicable rows use `-` and an outcome beginning `Not applicable:` with a reason. Unknown markers/dimensions, malformed tables, missing cells and undeclared/duplicate IDs reject.

Refer to a scenario using its model path and exact dimension label. Describe material combined hazards in concise requirement-linked prose nearby; no additional boundary/proof ID series is required. Delivery allocates every affected requirement, scenario and integrated hazard to concrete proof; structural checks cannot judge semantic adequacy.

## Architecture views

Every model needs an Architecture Overview with a concise graph. Orient readers to principal responsibilities, externally significant products or interfaces and the important relationships through which the system delivers and assures its outcomes. Enclose owned responsibilities in a model boundary; keep external owners, inputs and consumers outside. Label significant edges with the shared subject and purpose. Internal boxes represent actual responsibilities, not automatically services or new models.

For Context, Building Block, Runtime and Deployment, record whether the view is necessary, why, and where its detail belongs. Draw each necessary view. The overview may summarize these views, but cannot replace a necessary supporting view or become duplicate detailed authority. Resolve every material element and relationship to an owning section or model. Parents own child composition; child contracts own their internals. Reuse diagrams by reference and preserve anchors.

Keep decisions proportional: a small leaf still needs an overview, but may have a bounded reason for no deployment diagram. Reassess view necessity when relevant interfaces, behavior or environment change. Existing source authority remains applicable; feature/proof operation is unsupported and scoped adoption requires project authority; installation does not convert documents or adopt project governance. Standalone architecture/ADR output is outside this authoring method.

## Decisions and references

Record important decisions once in the owning model with stable identity, context, selected outcome, meaningful alternatives, consequences and still-applicable constraints. Explain why the choice fits the required behavior. Do not require a duplicate current ADR. Preserve requirement/decision references across revisions or give explicit replacement mappings. Retain historical decisions and judgments with their original subjects.

## Living test design

Use the project's declared shared test-design rules when present. A project may assign shared policy to its System/composition owner, with validation tooling owning execution. Declare the chosen owner explicitly rather than infer it from a directory or runner. Shared guidance may live in a separately declared supporting directory with that existing owner; model-specific strategies and scenarios remain with their models. Keep common rules in one authored location and link from model designs. This organizational choice adds no model identity and imposes no repository-specific path on customer projects.

Keep lasting coverage intent with its responsibility owner. A small model can use a section beside acceptance intent. When separate detail is useful, respect the project-selected layout and gather strategy and any adopted catalog under the model's `test-design/` directory. A practical layout is `M/M.md`, `M/test-design/test-design.md`, an explicit case index and `M/test-design/cases/<group>.json`. This is an organizational pattern, not permission to move an existing model or require JSON everywhere. Keep executable tests in their source owners.

Derive the account from current required behavior and plausible violations before copying existing method names. Use equivalence partitions, real ordered boundaries, decision tables, state transitions, properties or controlled faults as appropriate. Name the actual observation boundary separately from the derivation method. For each meaningful scenario give concrete starting conditions, the exercised action and independently expected values, diagnostics, preserved state or prohibited side effects. A helper needs direct coverage only when that boundary contributes useful protection.

Review the model's supported scope before expanding a large catalog. Keep one-time migration acceptance in its change and shared maintenance duties at their existing owners. Each additional scenario needs a distinct outcome, material failure boundary, regression or useful diagnostic contribution. Related field variations can share a scenario; different authority, persistence and recovery states retain independently understandable observations. Do not meet a case-count target by either multiplying trivial inputs or merging unrelated failures into a vague entry. Several executable methods can realize one scenario, and one composed test can support several obligations without duplicate execution. Native discovery owns the method inventory; no complete permanent method-to-case mapping is required.

Group scenarios by coherent responsibility and setup. Explain representative fixture roles, fresh mutable resources, cleanup and real versus substituted dependencies. Prefer ordinary test functions/framework groups and small fixture operations; use resource objects for a cohesive lifetime when useful. File length alone does not determine a split. Keep defining mutations and assertions visible; a fixture helper must not compute the expected answer using the operation being assessed.

Link actual source/test locations or a justified review/walkthrough procedure. Distinguish inspected existing assertions, partial protection and proposed cases; a link or passing suite cannot establish that a case detects its named defect. Establish valid negative-case setup before mutation and identify the intended rejection. Parent models reference child detail and add only their own meaningful interaction observations. A shared fixture or scenario has one primary owner.

When the user or project selects a structured case catalog, define its required fields/types, ownership, stable case and variant identities, explicit group membership, reference semantics, closed values and realization-gap meaning. Keep strategy, scenario data, executable assertions and execution results distinct. Explain what author checks establish and what still needs semantic review. Do not invent a schema consumer, runnable CLI command, approval or compatibility guarantee merely because JSON exists. Use the adopted project contract rather than copying another project's format by default.

Maintain the account when behavior, grouping, fixtures, source paths or execution reachability changes. Preserve identities through moves; reconcile current links/imports/discovery and preserve historical assessments with their original subjects. Remove obsolete cases only after the owner retires their obligation and resolves exclusive consumers. Variations need a distinct outcome or useful diagnosis; another release number alone adds no case. A missing catalog row does not justify deleting an existing regression.

Consolidating design entries preserves required observations, useful realization links and unresolved gaps. Record a deliberate consolidation's before/after obligation mapping with the change; do not create permanent aliases. Assess executable redundancy separately and establish retained protection before removing tests. Judge useful coverage, assertion quality, diagnosability and maintenance cost rather than raw case or line counts.

For handoff, inspect the exact owner and all affected strategy/catalog/group files together, alongside relied-on examples. Structural checks cover selected shape, references and discovery; independent review judges useful coverage and expected outcomes. Record actual results through the project's evidence owner rather than embedding run status in living test design.

## Supporting examples

The parent indexes each example's purpose, governing requirements, complete/excerpt scope and material synthetic identities or starting assumptions. Shared examples have one owner with consumer references. Load them on demand; they illustrate existing obligations and never become a second normative owner.

JSON examples must parse without explanatory invented fields. Complete records must conform to their selected schema when available; explicitly disclose absent-schema limits. Excerpts must state their omitted context and cannot claim complete-record conformance. Keep explanation in the parent or accompanying prose.

Before/after pairs must preserve the invariant they claim to demonstrate. Two individually valid records can still form an invalid transition; examine identity, authority, unchanged neighbors and prohibited side effects as applicable. Syntax checks do not establish the illustrated invariant.

Independent review covers affected examples alongside their owner, with exact identities when relied upon. Separately test the applicability contrast: if only a relied-on example changes, include its new exact subject and unchanged owning model in selection/handoff. Earlier approval of the parent or example does not by itself assess the revised example. Responsible assessors judge current reliance under existing review policy; selectors supply identities and retain model/example validation pairing, not automatic invalidation.

Keep one text source for a diagram and reference it; do not maintain competing inline/external copies. Images, external links or color alone cannot be the sole engineering truth. Keep examples free of secrets and private debug data.
