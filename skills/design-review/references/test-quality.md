# Test quality application

Use the selection method below when the selected Design authoring method creates or revises living test design. Other stages apply this guidance when the project explicitly adopts shared test criteria and the invoked work authors, allocates or assesses test obligations. Method use does not adopt project governance or a case catalog. Resolve the shared policy owner through the project's governance; execution tooling does not determine that ownership. The project's governing Design remains authoritative. Responsible specialists assess actual plans, tests and evidence under the project's review policy. This guidance grants no suite approval, evidence applicability, review waiver or execution permission. Historical contracts retain their meaning.

## Select requirements and proof

Apply these steps to every current requirement and section-owned responsibility within the selected model or change scope, including nonfunctional guarantees, public failures and prohibited effects. For a complete-model request, account for the current hierarchy; for a change, include affected producers, consumers and parent interactions. A CI path selector selects existing checks to run; it cannot establish that the necessary proof exists.

1. Identify the supported outcome and its governing requirement or justified engineering obligation. Split compound requirements into outcomes that need different observations without replacing their identities. Keep scoped migration proof at its actual adoption or correction point; completed historical work does not become a perpetual replay test. Preserve an unexplained regression while its owner settles the intended behavior.
2. Describe the plausible violation and consequence: which condition could produce a wrong result, lost state, crossed authority or hidden failure, and which observation would expose it? Derive protection from the contract before copying the existing suite. Include known defects and parent interactions that a requirement checklist could miss.
3. Choose depth and priority from consequence, plausible triggering conditions, exposure and recovery. Unauthorized writes, corrupted records, false completion and irreversible effects need strong failure or transition proof even when infrequent. Complexity, concurrency, recent changes and prior defects may justify additional distinctions. Use qualitative reasoning; no numerical risk taxonomy is required. Runtime cost and low frequency cannot waive required protection.
4. Choose repeatable automated observations for executable behavior and concrete independent inspection or walkthroughs for semantic judgment. Select the smallest boundary capable of exposing the violation while preserving any explicitly required broader observation. Explain what substituted dependencies leave unproved. Return an unobservable or contradictory requirement to its owner rather than inventing the expected result.
5. Select representative outcome partitions and relevant limits. Use decision alternatives when combinations change the rule, transitions when state changes the outcome, and controlled faults or interruption when partial effects or recovery matter. Group equivalent variations while keeping different failure mechanisms understandable. Properties may specify a generated domain and invariant without enumerating every input.
6. Connect each scenario to an independently expected result, a minimal realistic fixture and inspected existing or proposed realization. Check actual assertions and native discovery before claiming coverage. Requirements, scenarios and executable cases may relate many-to-many; no per-function record or complete method inventory is required. Preserve useful unlisted regressions: a catalog is not a test whitelist, and a link or passing method does not prove every claimed outcome.
7. Challenge the selected group with a concrete faulty candidate or inspected failure mechanism. Stop adding variations when each supported outcome and material hazard has sufficient observation and another case adds neither distinct detection nor useful diagnosis. Stop a completeness claim when a required outcome, owner, realization or observation is unresolved.

Keep the reasoning in existing group-level prose or tables: requirement/outcome, plausible violation and consequence, chosen conditions/action/observations, fixture strategy, realization and limits. Account for each current obligation through sufficient proof, an explicit proof gap or the responsible owner's bounded applicability or retirement disposition. A recorded gap is not satisfied protection. A small model can use Markdown alone; JSON is optional unless the user or project selects a catalog. This method adds no mandatory field schema, per-requirement ledger or case-count target. Actual execution and assessment remain separate evidence.

Parent models reference child coverage and add the interactions that can fail while each child still passes. Give a shared fixture or scenario one primary owner. Planning allocates milestone and integrated proof; implementation supplies fixtures and assertions. Missing intended behavior returns to Design, missing allocation to planning, and defective concrete tests to their implementation or correction owner.

## Fixtures and observation boundaries

Use the smallest realistic fixture that retains the protected failure mechanism. Every independently runnable case owns fresh mutable state and cleanup; shared immutable inputs may be copied before mutation. Keep an intentional sequence within one scenario instead of making tests depend on execution order. Make the defining condition and observation visible, including the intended rejection and required absence of side effects. Establish valid setup before changing the one condition under test so an unrelated fixture failure cannot masquerade as protection.

A mock or helper that bypasses public dispatch, persistence or an external interaction cannot prove that behavior. Retain real Git, filesystem, archive or process operations where their failure mechanism matters. Keep lower-level and integrated tests when their detection scope or useful failure localization differs. Named parameter rows can share a fixture shape when they test the same rule; another name or repeated assertion alone does not supply useful diagnosis. Do not manufacture Cartesian combinations or use test counts and coverage percentages as adequacy targets.

## Worked selection: atomic batch import

Assume a model requires a valid batch to persist completely and a rejected or failed batch to preserve the prior records, with an accurate failure diagnostic. These are the example's declared guarantees, not a universal rollback rule. Use a private record store containing an independently specified `keep` record, a valid two-record batch `A`/`B`, and literal expected records. Each variation starts fresh. Invoke the public import boundary and inspect persisted records independently of the importer's own expected-output calculation.

| Protected outcome | Conditions, action and independent observation | Fixture and realization limit |
| --- | --- | --- |
| Complete valid import | Import valid `A` and `B`; observe both persisted values, the unchanged `keep` record and complete-success result. | A real private store detects dropped writes that a parser-only check cannot observe. |
| Rejection preserves state | Change only `B` to violate a declared input rule; observe that specific rejection and the original record set, with neither `A` nor `B` added. | Establish the valid control first. Equivalent malformed values can be named variations within this group. |
| Failure preserves state and reports failure | Inject a controlled failure after the first write is attempted; observe the original records and the intended failure, never complete success. | Keep actual persistence in the observation. The fault trigger may be controlled; a fake store that promises rollback cannot prove rollback. |

The parent import flow owns the last composed observation: a parser and transactional storage helper can each pass while a faulty caller commits records individually. Keep this integration proof alongside useful child checks. A prior regression showing that a failed import deletes `keep` remains protected even if it has no catalog row; inspect its assertion before consolidating it into this group.

For a guidance-only authoring claim, independently compare a compliant Design with a candidate that permits partial import: the latter weakens the approved outcome. A different candidate that preserves the atomic guarantee but offers only parser checks leaves a persistence-proof gap. Record the actual candidate and assessment; headings and IDs can pass in both faulty candidates and provide only structural support. This illustrative walkthrough is not an executed assessment or universal agent-behavior proof.

## Check the oracle

Inspect how the setup and assertion distinguish correct behavior from the intended violation. A concrete counterexample or inspected failure mechanism should explain the detection. Expected results computed by the same potentially faulty production logic, assertions that cannot fail on the claimed defect and unchecked snapshot updates are insufficient. Mutation testing can help but is not a universal requirement.

Property-based and randomized tests are useful when they have a justified invariant, generated domain and relevant failure observation. Preserve enough counterexample and environment information to investigate or reproduce failure; a seed alone cannot reproduce uncontrolled external state. Concrete generated inputs need not all be enumerated in Design.

Test success does not replace independent review or determine whether evidence remains current. Optimize measured setup and execution cost while preserving required observations; cheaper execution alone does not establish adequate protection.
